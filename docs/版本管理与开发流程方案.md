## 0. 核心原则

1. **版本分层**：`MAJOR.MINOR.PATCH` 三层，大版本跨层必须全面审核，小版本/补丁必须有测试版本打底。
2. **先备份、再上线**：任何影响数据的操作前必须先做字节级备份并校验 magic。
3. **先审、后过**：大版本上线前执行「全面审核 + 系统性测试」，达标才准发。
4. **可视化、可回溯**：每个版本有明确看板（PLAN）、变更记录（CHANGELOG）、备份快照，随时可回滚。
5. **单人 + AI 协作**：不承诺日历天数，以「里程碑 / 轮次」为节奏单位。

## 1. 版本规划架构

### 1.1 三阶段开发策略

每个「功能域」的演进按三阶段推进；整体版本也遵循同一条「初版 → 拓展 → 优化」主线。

| 阶段                | 目标      | 典型内容                  | 当前项目映射             |
| ----------------- | ------- | --------------------- | ------------------ |
| **① 初版**（基础功能）    | 跑通核心闭环  | 聊天 + AI 接入 + 角色卡 + 记忆 | **v1.0.0 已完成并发布**  |
| **② 拓展升级**（功能扩展）  | 加能力、加玩法 | 记忆可见性、套话、群聊、角色差异化、自成长 | v1.1 / v1.2（☑ 序列内） |
| **③ 优化升级**（性能/体验） | 稳、快、好用  | 依赖升级、UI 打磨、性能调优、内存优化  | 每个大版本内的收尾阶段        |

> 注意：三阶段不是严格线性。每一个「大版本」内部可再套「拓展→优化」小循环；「优化」既可以是独立版本，也可以附着在某个功能版本收尾。

### 1.2 版本号定义规则

遵循 [CHANGELOG.md](../CHANGELOG.md) 已采用的语义化版本 `MAJOR.MINOR.PATCH`：

| 版本层           | 定义      | 示例            | 触发条件                          | 发布门槛                               |
| ------------- | ------- | ------------- | ----------------------------- | ---------------------------------- |
| **大版本** MAJOR | 完整稳定大版本 | 1.0 → 2.0     | 架构级变革 / 重大能力跃迁（本地模型、群聊、账号体系等） | **全面审核 + 系统性测试 + 全线里程碑**           |
| **小版本** MINOR | 稳定小版本   | 1.0 → 1.1     | 功能扩展 / 重要体验提升（记忆可见性、套话等）      | **≥5 个测试版本 + 回归测试**                |
| **补丁** PATCH  | 稳定补丁版   | 1.0.0 → 1.0.1 | 缺陷修复 / 紧急热修                   | **≥5 个测试版本**（紧急热修按 2.4 走快速通道，仍需验证） |

> 说明：用户示例「1.0.1-test1 \~ 1.0.1-test5」中的 `1.0.1` 对应**补丁版本（PATCH）**。本方案统一框架为：**任何稳定版本（小版本或补丁）正式发布前，默认至少走 5 个测试版本**；小版本以外、大版本之内按 MINOR 递增。

### 1.3 版本生命周期

```
需求入库 → 拆分任务点(PLAN) → 开发实现 → 测试版本(test1~testN) → 回归 → 稳定版发布 → 备份留档 → 更新 CHANGELOG
           ↑                                                          ↓
           └────────────────────（缺陷/新需求回流）────────────────────┘
```

## 2. 版本迭代管理

### 2.1 测试版本规则

- **命名**：`{目标稳定版本}-testN`，N 从 1 递增。例如目标发布 `1.1.0`，测试版本为 `1.1.0-test1` \~ `1.1.0-test5`。
- **数量**：每个稳定小版本 / 补丁发布前，**至少 5 个测试版本**（`test1`\~`test5`）。
- **每个测试版本必须可安装、可验证**，并产出验证记录（见 §7 测试流程规范）。
- **发布顺序**：`test1 → test2 → … → test5` →（通过全部 gate 后）→ 正式稳定版本。

### 2.2 备份策略

> 已由 `tools/backup_db.ps1` 落地（字节流 + magic 校验），本表固化保留规则。

| 版本类型               | 保留份数         | 说明                  |
| ------------------ | ------------ | ------------------- |
| **大版本**（X.0）       | **永久保留**     | 不清除，作为长期回滚点         |
| **稳定小版本**（X.Y，Y≠0） | 保留最近 **3** 份 | 超出的最老一份自动清理         |
| **测试版本 / 临时**      | 保留最近 **5** 份 | `temp` 目录，超出的最老自动清理 |

- 触发时机：**每次「功能 / 阶段确认」后**做一次备份；大版本与小版本发布前各做一次正式备份。
- 正确性保证：先 `am force-stop` → 字节流传速（禁用 PowerShell `>` 文本重定向）→ 校验 magic（db=`SQLite format 3`、wal=`37 7F 06 82`），不合法即报错、不产可恢复文件。

### 2.3 发布流水线（固定顺序）

1. 编译通过（`assembleDebug`，无阻断错误）
2. 全量 JVM 单测通过（`testDebugUnitTest`）
3. 迁移测试在安全环境通过（`assembleDebugAndroidTest`，**绝不跑在带正式数据的真机**）
4. 真机覆盖安装实测（`adb install -r`，保留数据）
5. 备份留档（字节级 + magic 校验）
6. 更新 CHANGELOG + 标签（tag）
7. 推送 GitHub

### 2.4 紧急热修快速通道（仅补丁）

- 适用：修复高危缺陷（崩溃、数据损坏、安全漏洞）。
- 要求：仍须「编译 + 单测 + 真机安装 + 备份」最小闭环；可压缩到 1\~2 个测试版本，但**须在 CHANGELOG 注明为何豁免 5 测试版本**，并留存证据。

## 3. 质量保障流程

### 3.1 大版本更新前的全面审核

跨大版本（如 1.x → 2.0）之前，**必须**执行：

1. **全面项目审核**：复用已有「项目全面审核报告」流程（逐项核对上轮遗留、代码质量、架构、性能、安全、测试覆盖）。
2. **系统性测试**：见 3.2。
3. **交付人工审核**：产出报告 + 简易操作流程指南 + 测试合格标准，交用户验收。

### 3.2 系统性测试维度（大版本必修，小版本按需裁剪）

| 维度        | 检查点                                                                              |
| --------- | -------------------------------------------------------------------------------- |
| **功能完整性** | 既有链路不回归（聊天/记忆/互动/说话打听/陪看）；新功能闭环（引擎+入口+UI+测试）                                     |
| **兼容性**   | 最低 API 29 与目标 API 36；Room 任意旧版本升级 0 崩溃；深浅色/不同屏幕                                  |
| **性能指标**  | 冷启动 ≤3s；常驻内存 ≤200MB；长会话滚动 60fps；流式 UI 帧 <16ms                                    |
| **安全漏洞**  | 密钥不进代码（Keystore/DataStore）；`baseUrl` 强制 HTTPS；无空 `catch{}`；Receiver 非导出；无硬编码敏感信息 |
| **数据完整性** | 迁移测试通过；备份可恢复且 magic 校验有效                                                         |

### 3.3 发布准入标准（gate，全绿才放行）

| 门槛    | 标准                                           |
| ----- | -------------------------------------------- |
| G1 编译 | `assembleDebug` / `assembleRelease` 通过，无阻断错误 |
| G2 单测 | `testDebugUnitTest` 全绿（当前基线 65 用例，只增不减）      |
| G3 迁移 | `assembleDebugAndroidTest` 编译通过；迁移测试在安全环境通过  |
| G4 真机 | `adb install -r` 覆盖安装成功，核心链路人工冒烟通过           |
| G5 备份 | 发布前备份完成且 magic 校验有效                          |
| G6 文档 | CHANGELOG 更新、tag 打好、PLAN 状态同步                |

> 「万无一失」= 上述 6 项 gate 全部绿灯。任何一项红灯即退回迭代，不得发布。

### 4.3 责任人（单人项目分工）

| 角色            | 责任                                   |
| ------------- | ------------------------------------ |
| **用户（Owner）** | 需求/方向拍板、验收审批、真机授权、开梯子（GitHub）、紧急热修决策 |
| **AI（执行方）**   | 实现、测试、报告、备份、文档同步                     |
| **（可选）专家评审**  | 涉及重技术方案（如 TTS、本地模型）时外审               |

### 4.4 跨版本功能优先级评估机制

用于决定「候选需求」何时、以何顺序纳入版本。按四维打分，总分高者优先：

| 维度       | 权重  | 评分依据                |
| -------- | --- | ------------------- |
| **价值 V** | 30% | 对核心体验/用户痛点的增益       |
| **成本 C** | 25% | 实现复杂度、代码改动范围（越低分越高） |
| **风险 R** | 25% | 迁移/性能/安全风险（越低分越高）   |
| **依赖 D** | 20% | 是否为后续功能的底座（地基分越高）   |

- 流程：候选需求 → 四维打分 → 排序 → 与用户确认后插入 PLAN 对应版本 → 拆分任务点。
- 原则：**地基优先**（如记忆可见性是套话/群聊前置，D 分高，优先）；**先轻后重**（低风险快速功能可插空提前，高风险重功能排后并先做可行性验证）。

## 7. 测试流程规范（细化）

每个「测试版本」固定执行以下动作并记录结果：

1. **编译**：`assembleDebug`（或对应 release）
2. **JVM 单测**：`testDebugUnitTest`，记录用例数（当前基线 65，只增不减）
3. **迁移测试**（涉及 schema 变更时）：`assembleDebugAndroidTest` 编译；迁移在安全环境跑
4. **真机安装**：`adb install -r`（覆盖保全数据），记录是否成功、是否崩溃
5. **核心链路冒烟**：会话列表→记忆页→互动中心→设置→聊天，人工点一遍
6. **备份**：`backup_db.ps1`，记录备份路径 + magic 校验结果

> 记录模板（每轮一条，写入对应版本验证笔记）：`版本 / 日期 / 编译 / 单测用例数 / 迁移 / 真机安装 / 冒烟 / 备份路径+magic / 结论`。

## 8. 风险应对策略

| 风险        | 影响                  | 应对                                                                   |
| --------- | ------------------- | -------------------------------------------------------------------- |
| Room 迁移崩溃 | 升级丢数据/闪退            | 迁移测试先跑 + 发布前备份 + 真机升版本回归；缺索引列须同时 ADD COLUMN+CREATE INDEX             |
| 真机数据被清    | 用户数据丢失              | 绝不在正式真机跑 `connectedDebugAndroidTest`；更新一律 `adb install -r`；动数据前先字节备份 |
| 二进制备份损坏   | 无法回滚                | 禁用 PowerShell `>` 文本重定向，用字节流；备份后校验 magic                             |
| 签名冲突      | release 覆盖 debug 失败 | release 与 debug 签名不同，真机首次装 release 需干净环境；记录于发布流程                     |
| 弱模型误实现    | 偏离需求                | 任务点原子化 + 单测护栏 + 每阶段人工审核                                              |
| 候选需求超前开发  | 返工/浪费               | 严守「拍板后才入库」；优先级四维评分后再立项                                               |
| 安全漏洞      | 密钥泄露/被攻击            | HTTPS 强制、密钥进 Keystore/DataStore、无空 catch、Receiver 非导出（审核 gate 覆盖）    |

## 9. 已确认结论（2026-08-28 用户拍板）

1. **测试版本命名**：采用 `{目标稳定版本}-testN`（如 `1.1.0-test1`）。用户示例 `1.0.1-test1` 中的 `1.0.1` 按「补丁版本（PATCH）」理解。
2. **测试版 vs 稳定版（关键澄清）**：用户手机日常装的**一直是测试版**（`app-debug.apk`，覆盖安装保留数据）；**稳定版**（`app-release.apk`）不装手机，而是**放到独立归档文件夹并做标识**，标注各自对应的稳定版本号。→ 见 §2.5「稳定版产物归档」。
3. **落地同步**：本方案已同步写入 PLAN.md（版本标注约定）与 ROADMAP.md（里程碑发布 gate）。
4. **下一版本优先级**：**v1.1（记忆可见性）作为下一主线启动**；「角色差异化 / 自成长」列为 v1.3 候选，排在 v1.1 之后，须可行性论证后再立项。
5. **责任人**：单人（用户）+ AI 执行，分工见 §4.3，无补充。

### 2.5 稳定版产物归档（对应用户「稳定版放文件夹、做标识」）

- **归档目录**：`F:\EdenCourt\releases\`（与 `F:\EdenCourt\backups\` 同级，仅本机，不入库）。
- **命名规则**：每个稳定版一个子目录 `{版本号}\`，内含 `app-release.apk` + `README.txt`（记录版本号 / 日期 / 签名 alias / 变更简介）。
- **机器上装什么**：手机始终装测试版 `app-debug.apk`（`adb install -r` 覆盖保全数据）。
- **何时归档**：稳定版发布（通过 §3.3 全部 gate）后，复制 release APK 到对应子目录并写标识。
- **保留策略**：大版本永久；小版本保留最近 3 份（与备份策略一致）。
