## 2. 用户核心诉求与质量标准

1. **质量标准**：用户明确希望语音「至少像星野 App 的角色语音」——即**云端 TTS 级别**：中文自然、带情感、多音色、接近真人对话。用户可接受端侧质量，但期望尽可能逼近。
2. **功能需求拆解**（用户逐条提出）：
   - **音色混合 / 音色自定义**（希望不限于固定音色）
   - **音调（pitch）可调**（希望说话有高低起伏、可控制语气）
   - **中英日三语**（至少能读这三种语言，中文为主）
3. **必做体验要求**（用户已提）：语音下载/播放要有可见反馈（横幅/进度提示）；TTS 预览支持自定义文本输入。

## 3. 现状与技术盘点

### 3.1 此前已定的三阶段路线（.planning/01\_设计讨论/TTS语音系统详细方案.md，2026-06-30）

```
pre-1.0：VITS(aishell3) 打包进 APK（~116MB，174 说话人）
v1.x  ：Kokoro-82M 主引擎 + Provider 多引擎（VITS/Kokoro/Matcha）+ 模型导入导出
v2.x  ：GPT-SoVITS 端侧（Rust+ONNX，~200MB，语音克隆）
```

### 3.2 对 VITS 的能力核查（用户的四个关注点）

| 需求    | VITS 原版 | 说明                                                              |
| ----- | ------- | --------------------------------------------------------------- |
| 效果    | 中等偏上    | 单阶段端到端（声学+声码器联合训练），非自回归、快、稳；英文 MOS≈4.4；中文非强项（社区用 Bert-VITS2 变体） |
| 音色混合  | ❌       | 说话人=查表 embedding（离散 ID），无官方混合接口；embedding 线性插值理论可行但开源实现少且不成熟    |
| 音色自定义 | ❌       | 需微调/训练新 speaker embedding，无零样本克隆                                |
| 音调    | ❌       | 无 pitch 参数，音高在潜在表示内不可外部调节                                       |
| 中英日三语 | ⚠️      | 架构语言无关，但取决于训练数据；原版仅英文，三语需专门多语模型                                 |

**结论：VITS 几乎不满足用户四项需求中的任何一项，需引入更灵活的引擎。**

## 5. 当前倾向路线（用户 2026-08-26 拍板：纯端侧为主，云端仅留接口）

```
端侧三引擎（Provider 多引擎可切换）
  ├─ Kokoro-82M  主引擎（音质保底）
  ├─ MeloTTS     多语（中英日韩）+ 自定义音色 → 补"三语/音色自定义"短板
  └─ VITS        现状（打包预置）
远期 v2.x：GPT-SoVITS 端侧（语音克隆 + 参考音频近似音色混合）
云端（Azure/火山/Edge）：仅保留 CloudTtsProvider 接口，不依赖、不强制、不预埋
```

**倾向理由**：

- 产品红线是离线可用 + 本地优先 → 语音不依赖网络、零 API 成本、隐私不出设备
- 端侧质量追求「端侧最优」（Kokoro/MeloTTS 级），星野级（云端）作为**预留升级路径**而非当前目标
- Provider 架构为将来接云引擎留好扩展点，用户可随时切换

## EdenCourt TTS 语音方案——专家评审整合与最终建议

### 一、核心结论

1. **引擎组合**：采用 **MeloTTS 为主引擎（中文优先，多语分模型动态加载） + Kokoro-82M 为辅引擎（英文保底）**，移除 VITS。远期仅将 GPT-SoVITS 作为实验性克隆引擎，不纳入主线。
2. **音色自定义**：放弃实时连续“音色混合滑块”，改为 **“预设多音色 + PC 端训练自定义 speaker embedding 导入”**。角色卡仅需选定一个基础音色，后续可进行音高/语速微调。
3. **音调控制**：端侧引擎均无原生 pitch 参数，采用 **“参考音频/多音色选择 + 轻量后处理 pitch shift”** 作为折中方案，提供有限但可用的语气调节。
4. **情感表现**：端侧无法达到“星野级”表演性，但可通过 **文本韵律标记、音高/语速微调预设、选择自然音色** 等手段提升自然度；真正的情感驱动留待 GPT-SoVITS 远期验证或云端升级。
5. **质量标准**：必须提前与用户对齐“端侧天花板”——清晰自然、不机械，而非表演级。若用户坚持更高要求，可保留云端 TTS 接口作为可选升级。

***

### 二、端侧可行性验证（骁龙 8+ Gen1 / 红米 K60）

| 引擎             | 模型大小       | CPU 实时率（预估）      | 内存增量       | 结论                  |
| :------------- | :--------- | :--------------- | :--------- | :------------------ |
| MeloTTS（中文单语言） | \~100MB    | >2×              | \~200MB    | ✅ 完全达标              |
| MeloTTS（日文/英文） | \~100MB/语言 | >2×              | \~200MB/语言 | ✅ 需动态加载，16GB RAM 足够 |
| Kokoro-82M     | 82M 参数     | >2×              | \~200MB    | ✅ 英文质量高，中文待实测       |
| GPT-SoVITS     | \~200MB+   | 0.5×\~1×（CPU 勉强） | \~500MB+   | ❌ 端侧过重，仅实验          |

**建议**：首发只集成 MeloTTS 中文模型，后续按需动态加载其他语言模型；Kokoro 作为英文备选，若 MeloTTS 英文效果可接受则可进一步精简。

**MeloTTS ONNX 转换**：社区已有 `melo-tts-onnx` 导出方案，但多语言是分模型，需逐个导出。需特别注意 **speaker embedding 必须作为动态输入**，才能支持后续自定义音色导入。单人工作量约 1\~2 天/语言。

***

### 三、音色自定义与混合的现实方案

#### 1. 角色卡语音设置流程（v1 冻结版本）

```
选择基础音色（预设 or 导入自定义） → 设置音高偏移（±2 半音） → 设置语速（0.8~1.2×） → 保存
```

- **预设音色**：MeloTTS 中文自带 10+ 说话人，可直接使用。
- **导入自定义音色**：通过 PC 端脚本训练生成 speaker embedding 文件（`.npy`），放入 App 指定目录，扫描后可选择。
- **不提供实时音色混合**：原因如下：
  - MeloTTS 的 speaker embedding 线性插值虽数学可行，但实际听感不稳定，易出现音色撕裂，无成熟开源方案。
  - 实时混合增加 UI 与计算复杂度，单人维护成本高。
  - 更实际的“混合”需求可通过 **PC 端训练新 embedding** 满足，相当于离线混合。

#### 2. 自定义音色训练工具（PC 端）

- 基于 MeloTTS 官方训练代码封装一个简单脚本，用户提供 5\~10 分钟干净语音，自动预处理、微调（或仅提取 embedding）、输出 `.npy` 文件。
- 若用户无技术背景，可提供简易 GUI 或详细文档；也可以由开发者代为训练几个常用音色（如温柔女声、低沉男声等）随 App 发布。

#### 3. 音高/语速后处理

- 在 TTS 输出音频上使用 **SoundTouch** 或 **RubberBand** 库进行全局 pitch shift 和 time stretch。
- 建议范围：音高 ±2 半音、语速 0.8\~1.2×，此范围内自然度损失较小。
- 可预设几个“情感微调”模板（见第五节），用户一键切换，降低使用门槛。

***

### 四、音调与情感控制策略

#### 1. 原生能力限制

VITS / MeloTTS / Kokoro 均无外部可调的 pitch 参数，韵律由模型内部决定。因此“音调滑杆”无法像云端 TTS 那样精确控制每个字的音高变化。

#### 2. 可行替代方案

| 方法                  | 实现难度            | 效果               | 建议            |
| :------------------ | :-------------- | :--------------- | :------------ |
| **参考音频情感驱动**        | 高（需 GPT-SoVITS） | 最佳，可转移情感/韵律      | 远期实验，不纳入 v1   |
| **多音色选择 + 微调**      | 低               | 中等，通过不同说话人模拟语气   | v1 核心手段       |
| **文本韵律标记**          | 低               | 可改善停顿、强调         | v1 建议支持简单标点策略 |
| **后处理 pitch shift** | 低               | 有限，适合整体语气倾向      | v1 提供滑杆       |
| **情感预设模板**          | 低               | 简单直观，如“平静/开心/严肃” | v1 强烈推荐       |

#### 3. 文本韵律增强

MeloTTS 对部分标点敏感，可在送入 TTS 前对文本做轻度预处理：

- 添加 `……` 表示犹豫、省略。
- 使用 `！？` 加强疑问、感叹语气。
- 逗号、句号自然停顿，可适当增加换行或空格来制造节奏。
- 注意不要过度插入符号，以免模型产生奇怪发音。

#### 4. 情感预设模板（UI 层面）

在角色卡语音设置中提供几个预设按钮，自动组合音高和语速参数：

| 预设 | 音高偏移  | 语速   |
| :- | :---- | :--- |
| 平静 | 0     | 1.0  |
| 开心 | +1 半音 | 1.05 |
| 严肃 | -1 半音 | 0.95 |
| 温柔 | 0     | 0.9  |
| 急切 | +1 半音 | 1.15 |

用户也可手动微调滑杆，满足个性化需求。

### 五、质量标准与现实预期

- **星野级（云端）**：具备强情感表演、丰富音色、自然停顿，通常由大参数模型 + 海量数据训练而成。
- **端侧 MeloTTS / Kokoro**：清晰度、自然度接近普通云 TTS，但**情感丰富度、表演性差距明显**。MeloTTS 中文发音准确、流畅，日常对话够用；Kokoro 英文质量高，但中文效果待实测。
- **用户预期管理**：在动工前务必与用户沟通，明确“纯端侧”意味着语音“自然不机械”，而非“有表演性”。若用户无法接受，可提供云端接口作为可选插件（不违反离线红线，因为默认端侧，用户手动切换云端）。

### 六、架构优化与引擎选择

#### 1. Provider 架构确认合理

```
TtsEngine 接口
├── MeloEngine（主引擎，中文/日文/英文分模型动态加载）
├── KokoroEngine（辅助引擎，英文高质量）
├── CloudEngine（可选，Azure/火山等，用户配置后启用）
└── (未来) GptSovitsEngine（实验性）
```

**路由策略建议**：

- 默认按语言自动选择：中文→Melo 中文模型，日文→Melo 日文模型，英文→Melo 英文模型（若效果不佳则回退 Kokoro）。
- 用户可在角色卡手动指定引擎（高级选项）。
- 云端引擎仅在用户主动配置 API Key 后出现，否则隐藏。

#### 2. 移除 VITS 的理由

- 被 MeloTTS 在中文质量、自定义音色能力上完全覆盖。
- 灵活性差，无法满足用户“音色自定义、音调”等需求。
- 增加包体积和维护成本，无实际收益。

#### 3. GPT-SoVITS 远期评估

- 模型重（200MB+），CPU 实时率勉强，集成复杂（需 Rust/ONNX 优化）。
- 仅在用户明确需要“语音克隆”或“参考音频情感驱动”时再投入。
- 建议先完成基础 TTS 功能，待用户反馈后再决定是否启动。

### 八、行动项清单（建议立即执行）

1. **模型验证**（最重要）：
   - 导出 MeloTTS 中文 ONNX，在 K60 真机测试实时率、音质、内存。
   - 试听全部预设音色，选出 3\~5 个最自然的作为默认推荐。
   - 对比 Kokoro 中文效果，决定是否在 v1.0 就引入 Kokoro 作为英文引擎。
2. **冻结 v1 功能范围**：
   - 不做实时音色混合，不做参考音频，不做云端强制。
   - UI 仅提供：音色选择、音高滑杆、语速滑杆、情感预设按钮、试听输入框。

   - 预留 `speakerEmbeddingPath`、`pitchShift`、`speed`、`referenceAudio`（未来）等字段。

### 九、风险与注意事项

- **MeloTTS 中文模型可能无法直接转换为 ONNX**：需测试社区转换脚本，必要时自行修改导出逻辑。
- **音高后处理可能降低音质**：控制偏移量在 ±2 半音内，并提供“重置”按钮。
- **多语言模型动态加载会增加复杂度**：建议 v1.0 只做中文，避免过早引入多引擎管理。
- **用户可能坚持实时混合**：若强烈要求，可尝试在 MeloTTS 上实现 embedding 插值（简单加权平均），但需明确告知效果不稳定，作为实验功能隐藏。

***

### 十、总结

**最终方案**：MeloTTS 中文主引擎 + Kokoro 英文辅助（视验证结果），角色卡语音通过"预设/导入音色 + 音高语速微调 + 情感预设"实现，放弃实时混合，保留云端接口。该方案在离线、端侧、质量、开发成本之间取得平衡，符合单人开发者 + AI 助手的实际条件。请立即着手模型验证和预期沟通，避免后期返工。
