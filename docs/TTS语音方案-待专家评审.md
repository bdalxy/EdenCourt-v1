## 1. 项目背景与硬约束

| 项 | 说明 |
| --- | --- |
| 产品 | **EdenCourt**：AI 角色陪伴 Android App，定位「像活在手机上的真人」。角色有性格、记忆（跨会话/按角色隔离）、可跨会话打听与角色间互动（手动/自动） |
| 技术栈 | 纯 Kotlin + Jetpack Compose + Room/DataStore；单 Activity；本地优先（记忆/互动/关系全在端侧，无后端） |
| 开发模式 | 单人开发者 + AI 助手；功能按任务点推进 |
| 目标设备 | 红米 K60（骁龙 8+ Gen1，16GB RAM，512GB），Android 离线可用是产品红线 |
| 推理运行时偏好 | **ONNX Runtime / sherpa-onnx**（已有 TTS 方案文档基于 sherpa-tts；Android 端友好，支持 VITS 等多引擎的 ONNX 模型池） |
| 架构规划 | **Provider 多引擎 TTS**：本地引擎可切换（VITS/Kokoro/Matcha 已讨论），未来可挂云引擎 |
| 版本状态 | 当前 v1.2b（记忆可视化/互动/好感度/自动驱动已落地）；语音属于远期（ROADMAP 2.3 多模态），**尚未动工** |

## 2. 用户核心诉求与质量标准

1. **质量标准**：用户明确希望语音「至少像星野 App 的角色语音」——即**云端 TTS 级别**：中文自然、带情感、多音色、接近真人对话。用户可接受端侧质量，但期望尽可能逼近。
2. **功能需求拆解**（用户逐条提出）：
   - **音色混合 / 音色自定义**（希望不限于固定音色）
   - **音调（pitch）可调**（希望说话有高低起伏、可控制语气）
   - **中英日三语**（至少能读这三种语言，中文为主）
3. **必做体验要求**（用户已提）：语音下载/播放要有可见反馈（横幅/进度提示）；TTS 预览支持自定义文本输入。

## 3. 现状与技术盘点

### 3.1 此前已定的三阶段路线（.planning/01_设计讨论/TTS语音系统详细方案.md，2026-06-30）

```
pre-1.0：VITS(aishell3) 打包进 APK（~116MB，174 说话人）
v1.x  ：Kokoro-82M 主引擎 + Provider 多引擎（VITS/Kokoro/Matcha）+ 模型导入导出
v2.x  ：GPT-SoVITS 端侧（Rust+ONNX，~200MB，语音克隆）
```

### 3.2 对 VITS 的能力核查（用户的四个关注点）

| 需求 | VITS 原版 | 说明 |
| --- | --- | --- |
| 效果 | 中等偏上 | 单阶段端到端（声学+声码器联合训练），非自回归、快、稳；英文 MOS≈4.4；中文非强项（社区用 Bert-VITS2 变体） |
| 音色混合 | ❌ | 说话人=查表 embedding（离散 ID），无官方混合接口；embedding 线性插值理论可行但开源实现少且不成熟 |
| 音色自定义 | ❌ | 需微调/训练新 speaker embedding，无零样本克隆 |
| 音调 | ❌ | 无 pitch 参数，音高在潜在表示内不可外部调节 |
| 中英日三语 | ⚠️ | 架构语言无关，但取决于训练数据；原版仅英文，三语需专门多语模型 |

**结论：VITS 几乎不满足用户四项需求中的任何一项，需引入更灵活的引擎。**

## 4. 候选方案对比（结合 K60 端侧/本地/中文优先）

| 方案 | 多语(中日英) | 音色混合/自定义 | 音调可调 | 端侧可行性 | 说明 |
| --- | --- | --- | --- | --- | --- |
| **VITS** | ⚠️需数据 | ❌ | ❌ | ✅ 轻量 | 现状；工程质量稳、效果中上 |
| **Kokoro-82M** | ✅ 英日西法中印韩 | ❌ 固定 voice pack | ❌ | ✅ 轻量(82M) | 2025 年 TTS Arena 第 1，音质好；无克隆/混合/音调 |
| **MeloTTS** | ✅ 中英日韩西法 | ✅ 可训练自定义说话人 embedding（可插值） | ❌ | ✅ 轻量，可转 ONNX | **多语+自定义音色的端侧最佳平衡**，MIT |
| **GPT-SoVITS** | ✅ 中日英韩粤台 | ✅ 5 秒参考音频克隆；参考音频加权近似混合 | ❌(靠参考音频情感) | ⚠️ 重(~200MB+)，CPU 勉强 | 中文克隆最强；用户提到的「gpt 那个」 |
| **OpenVoice v2** | ✅ | ✅✅ 明确支持音色混合+克隆 | ❌ | ❌ PyTorch | 音色混合正解，端侧难 |
| **Edge-TTS** | ✅ 200+ 音色 | ❌ | ✅✅ 有 pitch/rate | ✅(需联网) | 音调调节最简单，但云端+非本地 |
| **Azure TTS** | ✅ | ❌ | ✅✅ | ✅(需联网+成本) | 商业云，中文音色多，接近星野 |
| **CosyVoice(阿里)** | ✅ 中英日韩西粤 | ✅ 零样本克隆+指令控制 | ❌ | ❌ ~2GB | 功能全，服务端 |
| **XTTS-v2(Coqui)** | ✅ 20+语 | ✅ 6 秒参考克隆 | ❌ | ⚠️ 模型大，已停更 | 克隆强，维护风险 |
| **F5-TTS** | ✅ | ✅ 零样本克隆 | ❌ | ❌ 模型大 | 效果接近 GPT-SoVITS，端侧难 |
| **Bert-VITS2** | ⚠️ 中英日 | ❌ 固定说话人 | ❌ | ⚠️ 中等 | 中文质量好，灵活性不足 |
| **Sherpa-onnx 模型池** | ✅ 含中文多说话人 | ❌ 固定 | ❌ | ✅ Android 友好 | 是推理框架+模型池，VITS 等引擎的承载者 |

## 5. 当前倾向路线（用户 2026-08-26 拍板：纯端侧为主，云端仅留接口）

```
端侧三引擎（Provider 多引擎可切换）
  ├─ Kokoro-82M  主引擎（音质保底）
  ├─ MeloTTS     多语（中英日韩）+ 自定义音色 → 补"三语/音色自定义"短板
  └─ VITS        现状（打包预置）
远期 v2.x：GPT-SoVITS 端侧（语音克隆 + 参考音频近似音色混合）
云端（Azure/火山/Edge）：仅保留 CloudTtsProvider 接口，不依赖、不强制、不预埋
```

**倾向理由**：
- 产品红线是离线可用 + 本地优先 → 语音不依赖网络、零 API 成本、隐私不出设备
- 端侧质量追求「端侧最优」（Kokoro/MeloTTS 级），星野级（云端）作为**预留升级路径**而非当前目标
- Provider 架构为将来接云引擎留好扩展点，用户可随时切换

## 6. 开放问题（请专家评审的核心）

1. **端侧可行性**：骁龙 8+ Gen1（K60）上，Kokoro-82M / MeloTTS / VITS 的 CPU 实时率与内存占用是否都达标（实时率目标 >1×，内存增量 <200MB）？MeloTTS 是否有现成 ONNX 转换路径？
2. **音色混合/自定义的现实路径**：端侧（无 Python 训练管线、单人维护）做「自定义音色」是否现实？MeloTTS 的自定义 speaker embedding 训练工作量与效果如何？「embedding 插值做音色混合」在 MeloTTS 上是否可用、效果是否可接受？还是说端侧应该放弃「混合」只保留「预设音色」？
3. **音调控制**：端侧引擎普遍无 pitch 参数，「用参考音频/情感控制替代音调滑杆」是否合理？有无被低估的端侧方案支持 pitch？
4. **质量标准现实性**：端侧 TTS 与「星野级」（云端）的实际可感知差距有多大？用户「至少像星野」的目标，在纯端侧约束下是否只能妥协？是否有我们遗漏的、能在端侧逼近星野的方案？
5. **架构**：Provider 多引擎 + 云端仅留接口的设计是否合理？有无更优的分层（如按内容类型/角色自动选引擎）？
6. **路线取舍**：三引擎（Kokoro+MeloTTS+VITS）是否冗余？是否应精简为「Kokoro（保底）+ MeloTTS（多语自定义）」二引擎 + 远期 GPT-SoVITS？GPT-SoVITS 在 K60 端侧是否现实（实时率/内存）？
