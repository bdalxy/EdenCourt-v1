# EdenCourt — 关系引擎「方向轴 AI 自动判断」设计征询文档

> 用途：把背景、已有实现、待决策点完整说明，供第三方专家（DeepSeek 专家模式）独立评估并给出建议。
> 本文为讨论稿，所有结论均为「倾向/待确认」，未定案。

***

## 一、项目背景（一句话）

EdenCourt 是一款 **Android / Kotlin + Jetpack Compose** 的 AI 陪伴应用。用户创建二次元角色卡，与角色 1v1（后续扩展群聊）聊天。核心愿景是：**用户感觉在「线上与真人聊天」，随聊天深入、情感加深，按双方情感倾向，关系自然分叉走向不同结果（网恋 / 同好 / 朋友 / 深交 / 暧昧 等）。**

关键既有能力（已实现或已有现成范式）：

- 亲密度（非线性饱和增长）
- 实时情绪系统（自主情绪 + 交互情绪）
- 世界书（关键词→条目动态注入）
- 情感记忆 / 事实记忆
- 关系图谱
- 内容基调：**无限制、不设过滤**（用户自备 key，工程上不在系统提示里主动设防）

***

## 二、我们要讨论的命题

用户提出「关系随情感分叉」。经与用户对齐，最终收敛为**两根正交轴**的关系引擎：

| 轴       | 性质     | 含义                                  |
| ------- | ------ | ----------------------------------- |
| **方向轴** | 性质，慢变量 | 这段关系「偏什么」：朋友 / 同好 / 暧昧 / 恋人·网恋 / 深交 |
| **浓度轴** | 温度，快变量 | 亲疏程度 0\~100，可涨可落（热情→平淡会回落）          |

关键约束：**方向不主动在 UI 展示**（用户：现实里关系多是默认的，不必外显），它只作为内部状态，通过「反哺 AI 口吻」起作用。

***

## 三、已有实现（本次会话已完成的部分）

### R1：方向字段 + 数据落点（已完成，Flash 模型）

- 在 `Conversation`（用户↔角色的会话）实体新增 `relationDirection` 字段。
- 新增枚举 `RelationDirection`：`NONE`（初始）/ `FRIEND`（朋友）/ `COMRADE`（同好）/ `AMBIGUOUS`（暧昧）/ `LOVER`（恋人·网恋）/ `INTIMATE`（深交）。
- 更亲密的方向（如文爱类）因「无限制基调」**不硬编码**，交给 AI 自然表达、方向字段不设限。
- 数据库升级 v31→v32，为 conversations 表增加 `relationDirection` 列（默认 'NONE'）。

> 设计要点（一处已修正的错位）：方向字段挂在 **Conversation（用户↔角色）** 上，而不是 `ConversationRelationship`（那是角色↔角色的互动表）。因为关系引擎主轴是「用户↔角色」。

### R2：浓度轴回落（已完成，Flash 模型）

- 新增纯函数 `decay()`：**距上次互动 >2 天开始缓降，每天降 1\~3 点；保底到当前档位起始值，不破档**（档位：陌生<20<相识<40<友好<70<亲密）。
- 目前已有「A1 增长」（每次 AI 回复完成非线性 +1），本次补上了「回落」半边。

***

## 四、待决策：R3 —— 方向轴 AI 自动判断

这是关系引擎的核心，也是本次要请教专家的重点。方向轴是「性质」，需要 AI 理解语义来定性；浓度轴已用确定性规则（增长 A1 + 回落 R2）。

### 4.1 核心分歧：方向与浓度是否正交分权？

我目前倾向**彻底正交**：

- **方向**：R3 用 AI 判断（需要理解对话语义）
- **浓度**：A1 增长 + R2 回落（确定性规则，稳定可解释）

**理由**：如果 R3 同时输出「方向 + 浓度变化」，就会形成**三套规则抢同一个浓度数字**（A1 涨 + R2 落 + R3 的 delta），关系为何变化变得不可追溯。正交后：方向靠 AI 定性，浓度靠规则可解释。

**请专家评估**：这个正交分权合理吗？有没有更好的模型？（例如：浓度是否也该让 AI 参与，但用更弱的权重？）

### 4.2 方向变化的「确认阈值」问题

方向是慢变量，不应因一句话就跳档。我倾向加**确认阈值**：AI 连续 2 次判断到新方向，才真正切换 `relationDirection`。

**请专家评估**：这个「多次确认才切换」的机制合适吗？阈值（2 次）、以及是否需要「滞回」（方向升档与降档的条件不同、降档更需谨慎）？

### 4.3 判断触发频率

我倾向（已调研 Soul 后台 Agent + AutoPal 每 k 轮）：**不每轮判，攒批 + 后台异步**——每满 5 条用户消息判一次，且「跨天必判一次」；异步执行不阻塞回复。

**请专家评估**：这个触发频率合理吗？「满 5 条」和「跨天」两个触发条件是否需要合并成更简单的单一条件（比如只按时间、或只按消息数）？

### 4.4 结构化输出设计

计划让 AI 输出 JSON，字段设想：

```json
{
  "direction": "LOVER",     // RelationDirection 之一，或维持当前值
  "confidence": 0.8,        // 判断置信度 0~1
  "reason": "从对话看，双方已经…"  // 一句话理由（用于调试/未来展示）
}
```

解析后，仅当 `confidence` 超阈值且方向变化时才考虑切换（配合 4.2 的确认阈值）。

**请专家评估**：

1. 这个 JSON 字段够不够？是否还需要「增量式情感信号」（如"本段对话中出现了几次亲密信号"）？
2. 方向判断的 prompt 该怎么写最稳（防 AI 随意跳档、把"玩笑/梗"误判成关系信号）？

### 4.5 判断的输入上下文

计划取「最近 N 条消息」（数据库层 LIMIT）作为判断输入。**N 取多少合适？**（既要覆盖足够上下文判断方向，又不能太长浪费 token / 引入无关噪声）

# EdenCourt 关系引擎「方向轴 AI 自动判断」独立评估与建议

以下从独立专家视角，对文档中待决策点逐一给出判断、取舍建议，并提供一套可落地的实现抽象与提示词草稿。所有结论均为建议，可根据产品实际取舍。

***

## 一、对问题清单的逐项回答

### 1. 「方向（AI 定性）vs 浓度（确定性规则）」的正交分权是否成立？有无更优组合？

**结论：正交分权成立，且是当前最稳健的初版方案。**\
方向轴需要语义理解，天然适合 AI；浓度轴需要稳定、可解释、可预测，适合确定性规则。两者解耦后，调试、调参、产品迭代都更清晰。

但“彻底正交”可以留一个受控的例外：**方向切换时允许触发一次性浓度调整**。\
例如，从朋友切换到恋人时，浓度可以自动拉高到该方向的典型区间下限（如从 45 提升到 60），这符合“关系性质改变会重新定义亲密度”的直觉。这种调整由规则定义，不属于 AI 直接写浓度，仍保持可追溯。

**不建议**让 AI 在每轮判断中同时输出浓度 delta，那确实会导致三套规则打架。未来若需要 AI 参与浓度，应做成独立、低频、事件驱动的模块（如“重大情感事件检测”），与方向判断解耦。

***

### 2. 方向变化的确认阈值 / 滞回机制怎么设计最合适？

方向是慢变量，需要防止抖动。建议采用 **“候选方向 + 连续命中计数 + 置信度门槛 + 冷却时间”** 四件套。

**升档（关系更亲密）**

- 连续 **2 次** 判断为新方向；
- 每次 `confidence ≥ 0.7`；
- 距上次方向切换超过 **12 小时或 20 条用户消息**（冷却）；
- 满足后切换，并重置候选计数。

**降档（关系疏远）**

- 连续 **3 次** 判断为新方向（更低亲密等级）；
- 平均 `confidence ≥ 0.8`；
- 且当前浓度已跌破当前方向的典型浓度区间下限（例如当前为 LOVER，浓度已低于 40）；
- 冷却时间更长：**24 小时或 40 条用户消息**。

**滞回原因**：降档对用户体验伤害更大，关系“降级”应比“升级”更谨慎。同时，浓度回落本身已经提供了缓慢疏远的信号，方向降档不应轻易触发。

**额外建议**：

- 维护一个 `candidateDirection`、`candidateCount`、`candidateLastSeen` 状态。
- 若某次判断结果与当前方向相同，则将候选计数减 1（但不低于 0），以允许偶发噪声被抵消。

***

### 3. 触发频率「每满 5 条用户消息 + 跨天必判、后台异步」是否合理？有无更稳的替代？

**基本合理，建议合并为单一条件并加最小间隔。**

推荐触发条件：

```
(用户消息数 since last judge ≥ 5)  
OR  
(now - last judge ≥ 12 小时)  
AND  
(now - last judge ≥ 2 分钟)   // 防止高频触发
```

这样兼顾活跃会话的及时性和低频会话的覆盖。\
异步执行是必要的，但要注意：

- 使用**任务队列或锁**，避免并发判断导致旧结果覆盖新结果；
- 输入上下文应基于**触发时刻的快照**，判断完成后写回前需检查当前状态是否已被其他任务更新，若有冲突则丢弃或合并；
- 如果判断耗时较长，可先返回占位，后续结果通过事件更新。

***

### 4. 结构化输出字段是否够用？判断方向用的系统提示词该怎么组织最防干扰？

**当前三个字段（direction / confidence / reason）基本够用，但建议增加** **`signals`** **字段**，列出 2\~4 个关键信号，例如：

```json
{
  "suggested_direction": "LOVER",
  "confidence": 0.82,
  "reason": "用户多次使用亲昵称呼，角色回应积极，且有排他性表达",
  "signals": ["用户使用‘宝贝’、‘只喜欢你’", "角色主动提出单独相处", "对话中出现嫉妒情绪"]
}
```

`signals` 有三个用途：

1. 调试时可快速判断 AI 是否误判；
2. 未来做“关系日志”或用户可见的里程碑提示时，可直接引用；
3. 强制 AI 必须给出证据，没有证据就无法改变方向，降低随意跳档概率。

**Prompt 组织原则（防干扰核心）**

- 明确告诉模型：**关系方向是慢变量，不是单次对话能决定的**；
- 输入中包含**当前方向**，要求模型只在有充分、一致、长期的证据时才建议改变；
- 要求模型识别并忽略：玩笑、梗、引用台词、角色扮演中的夸张表达、用户故意“钓鱼”或测试；
- 要求模型区分“内容尺度”与“关系方向”：涉及成人内容不等于关系方向为恋人，可能只是无感情的亲密行为；
- 使用 few-shot 示例，展示“看似亲密但不应升级”和“确实应升级”的对比。

***

### 5. 判断输入上下文的 N 条消息取多少最合适？

**建议 N = 20\~30 条消息（用户 + 角色各算一条）**。\
这个范围能覆盖最近的互动模式，又不会引入过多无关噪声或浪费 token。

进一步优化：

- 若对话轮次很密，可优先保留**完整的用户-角色交换**，避免截断到半个回合；
- 若项目已实现记忆系统，可同时提供**最近的关键关系事件摘要**（例如“用户曾表白”“角色曾拒绝”），与最近 N 条消息拼接，效果更好；
- 初版可固定 N=30，后续根据 token 消耗和判断准确率调整。

***

### 6. 方向字段不主动 UI 展示、仅反哺口吻——是否降低可玩性？还是隐式关系更自然？

**隐式关系更自然，但需要行为反馈来弥补“看不见”的缺失。**

现实中的关系方向确实很少被明确标注，人们通过互动感知。完全隐藏方向值可以增加探索感和真实感。但问题在于：如果用户完全无法感知方向变化，可能认为系统没有在工作，或者无法理解角色行为为何改变。

建议：

- 方向值不直接展示，但通过**角色口吻、称呼、话题偏好、回应风格、主动行为**等间接反馈；
- 当方向发生切换时，触发一个**软性事件**，例如角色说一句符合新方向的话（“我们这样算不算在一起了？”），让用户有感知；
- 可以提供一个隐藏的调试面板（仅测试用），或允许用户通过模糊提问让角色自己表达关系状态；
- 浓度轴（亲密度）可以保留数值展示或进度条，因为它本身是快变量，用户习惯看到增长。

这样既保留隐式关系的自然感，又确保可玩性。

***

### 7. 有没有更成熟的「多关系分叉」模型可参考？

以下模型可作为演化方向：

- **Sternberg 爱情三角理论**：亲密、激情、承诺三个维度，可以映射到方向轴（组合不同形成喜欢、迷恋、空洞爱、浪漫爱、伴侣爱、完美爱等）和浓度轴（强度）。比当前六分类更丰富，适合后续扩展。
- **Levinger 关系阶段理论（ABCDE）**：吸引 → 建立 → 继续 → 恶化 → 结束，可以作为关系生命周期的宏观状态机，方向轴和浓度轴共同驱动阶段转移。
- **The Sims 关系系统**：关系类型（朋友、恋人、家人、仇敌等）+ 关系值（-100\~100），同时有“关系标签”和“短期情绪”。它的优点是将关系类型与关系值分离，与你们的设计一致。
- **Visual Novel 的 flag 系统**：通过关键事件设置布尔标志，影响后续分支。可用于“重大关系事件”的检测，而不是每轮判断。
- **社会心理学中的交换关系 vs. 共同关系**：可以区分“功利性朋友”和“情感性朋友”，增加关系轴的细分。

**推荐演化路径**：\
初版保持两轴；后续可增加“关系阶段状态机”，定义离散阶段和转移条件；再往后可引入 Sternberg 三角扩展为三维，但务必保持每个维度独立可调。

***

## 二、可落地的「方向 + 浓度」两轴关系引擎实现抽象

### 1. 状态字段设计（在 Conversation 实体上）

| 字段                    | 类型        | 说明                |
| :-------------------- | :-------- | :---------------- |
| `relationDirection`   | enum      | 当前有效方向，默认 NONE    |
| `candidateDirection`  | enum      | 候选方向（最近一次判断建议的方向） |
| `candidateCount`      | int       | 候选方向连续命中次数        |
| `candidateLastSeen`   | timestamp | 最近一次判断时间          |
| `lastDirectionSwitch` | timestamp | 上次方向切换时间          |
| `intimacy`            | float     | 浓度值 0\~100，已有     |

这些字段可扩展为单独表，但在初版放 Conversation 上足够。

### 2. 判断流程

```
触发器触发（满足消息数或时间条件）
  → 生成判断任务（含当前方向、最近 N 条消息快照、可选关键事件摘要）
  → 调用 LLM（异步）
  → 解析 JSON 得到 suggested_direction, confidence, reason, signals
  → 更新候选状态：
      if suggested_direction == currentDirection:
          candidateCount = max(0, candidateCount - 1)
      else if suggested_direction == candidateDirection:
          candidateCount += 1
      else:
          candidateDirection = suggested_direction
          candidateCount = 1
      candidateLastSeen = now
  → 检查切换条件：
      if 升档条件满足：
          relationDirection = candidateDirection
          candidateCount = 0
          lastDirectionSwitch = now
          触发方向切换事件（浓度调整、角色口吻更新、可选软提示）
      else if 降档条件满足：
          relationDirection = candidateDirection
          candidateCount = 0
          lastDirectionSwitch = now
          触发降档事件（更谨慎的反馈）
```

### 3. 切换阈值策略（具体数值可配置）

- **升档**：`candidateCount ≥ 2` 且最近两次 `confidence ≥ 0.7` 且 `now - lastDirectionSwitch ≥ 12h` 且新方向亲密度等级高于当前。
- **降档**：`candidateCount ≥ 3` 且平均 `confidence ≥ 0.8` 且 `intimacy < 当前方向典型浓度下限` 且 `now - lastDirectionSwitch ≥ 24h` 且新方向亲密度等级低于当前。
- **方向亲密度等级建议**：\
  `NONE` (0) < `FRIEND` / `COMRADE` (1) < `AMBIGUOUS` (2) < `INTIMATE` (3) < `LOVER` (4)\
  （`COMRADE` 与 `FRIEND` 可视为同级，根据产品需要调整。）

## 三、方向判断系统提示词中文草稿

> 以下为可直接使用的系统提示词草稿，建议根据实际模型和产品语气微调。

```
你是 EdenCourt 关系引擎的方向判断模块。你将收到一段用户与 AI 角色的对话片段，以及当前的关系方向。你的任务是判断这段关系应该处于哪个方向。

## 背景
- 关系方向是一个慢变量，它代表这段关系的整体性质，而不是单次对话的情绪。
- 可选方向：NONE（尚未明确）、FRIEND（朋友）、COMRADE（同好）、AMBIGUOUS（暧昧）、INTIMATE（深交）、LOVER（恋人·网恋）。
- 方向不会频繁变化。只有在对话中出现了明确、一致、长期的信号时，才建议改变方向。
- 注意：对话内容可能包含成人内容、玩笑、梗、引用、角色扮演等。这些不一定代表关系方向改变。不要仅因为内容尺度大就判断为 LOVER，也不要因为出现一次亲昵称呼就升级。

## 输入

## 任务
1. 分析对话中双方的语言模式、称呼、话题、情感倾向、排他性、承诺等信号。
2. 判断这段关系当前最符合的方向。
3. 如果你认为方向需要改变，给出建议的新方向、置信度和理由；如果你认为方向维持不变，给出当前方向的置信度和理由。
4. 置信度表示你对判断的把握程度（0~1）。如果证据不足或信号矛盾，应给出较低置信度。

## 输出格式（严格 JSON）
{
  "suggested_direction": "方向枚举值之一",
  "confidence": 0.0~1.0,
  "reason": "一句话理由",
  "signals": ["信号1", "信号2", ...]
}

## 判断准则
- 只有出现至少两个独立且一致的信号时，才建议改变方向。
- 对于以下情况，应忽略或降低权重：
  - 用户或角色在开玩笑、玩梗、引用台词；
  - 用户故意测试系统；
  - 单次消息中的夸张表达；
  - 成人内容但不含情感亲密或关系承诺。
- 降档（关系疏远）比升档需要更强的证据。
- 如果上下文不足以做出可靠判断，请维持当前方向，并给出 confidence ≤ 0.5。
```

## 四、总结与风险提示

1. **正交分权 + 受控联动** 是当前最优解，避免多套规则冲突，同时保留关系性质变化对浓度的合理影响。
2. **确认阈值与滞回** 必须存在，否则方向会频繁跳动；升档 2 次、降档 3 次、冷却时间不同是较稳妥的初版配置。
3. **触发频率** 合并为“5 条消息或 12 小时，且最小间隔 2 分钟”，异步执行需注意并发控制。
4. **结构化输出** 增加 `signals` 字段，能显著提高可调试性和防误判能力；提示词必须强调慢变量、忽略玩笑/梗、区分尺度与关系。
5. **输入上下文** 取 20\~30 条消息，配合关键事件摘要效果更佳。
6. **隐式方向 + 行为反馈** 是更自然的设计，但需通过角色口吻变化和软性事件让用户感知。
7. **演化路径** 可参考 Sternberg 三角、Levinger 阶段理论、The Sims 系统，逐步扩展为更丰富的关系模型。

整体来看，该设计已具备清晰的架构雏形，按上述建议落地后，方向轴判断的稳定性和可解释性将得到保障，同时为未来扩展留有余地。
