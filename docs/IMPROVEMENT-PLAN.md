### 1.3 关键瓶颈与根因

1. **瓶颈一：真人感「三支柱」未立**（P-01/02/03）——产品已具备性格/记忆/主动，但缺「生活时间线、自发动机、关系事件」三个让角色"活起来"的地基。根因：MVP 聚焦"能聊能记住"，未触及"角色有自己的生活节奏"。
2. **瓶颈二：新用户冷启动失败**（P-04）——功能跑得比引导快，入口深、无开场仪式。根因：以"功能可用"而非"体验完整"为验收口径。
3. **瓶颈三：体验可靠性靠"模型自觉"**（P-05/06）——人设/记忆引用均无确定性机制兜底。根因：无本地约束层、检索与触发策略偏简单。
4. **瓶颈四：工程质量缺口**（P-07/08/09）——数据增长性能、自动化回归、发布收尾欠账。根因：单人开发以"功能推进"优先，工程债后置。

## 2. 改进方案设计

> 每个方案给出：解决的问题、核心改进点、实施范围、预期效益、方案变体（可选）。

### 方案 A · 角色时间线生活系统（解决 P-01）

- **核心改进点**：为每个角色建立「生活状态机」——按真实时间线自动切换状态（睡眠/晨起/日常活动/工作学习/社交/休息），状态影响：① 回复时机与语气（深夜被叫醒会困倦）；② 会话列表角色卡片显示「此刻状态」；③ 主动互动时机（不在睡眠窗口硬触发）。数据源：角色卡设定 + 可配置作息表 + 真实时间。
- **实施范围**：新增 `CharacterSchedule` 状态机（实体/配置）+ ChatScreen 状态展示 + 与 T11.7 自动驱动联动（睡眠窗口不串门）。
- **预期效益**：玩家随时打开都知道"TA 在干嘛"——真人感最直接、可感知的提升；为 B/C 提供"生活场景"素材。
- **变体**：A1 轻量（仅状态机+展示，不动对话行为）· A2 完整（状态参与 prompt 与互动调度）。
- **关于「角色观察用户」的定论（用户批注 2026-08-26 + 审阅处理）**：用户的直觉有价值——角色存在于用户设备上、某种程度上「一直陪在身边」、未来还能控制设备。但**不做「用户行为观察」（含定时观察）**：① 需额外权限（解锁/前台 App/位置/剪贴板）的采集触碰隐私与信任边界，与「陪伴感」基调相悖；② 单人项目难以可靠推断用户状态，易变「监视感」；③ 会让「角色有生活」跑偏成「角色盯着你」。用户直觉的正确落点是「记得用户」而非「看见用户」——见下方 **方案 A'（软感知陪伴）**。

### 方案 A' · 软感知陪伴（承接用户批注「一直陪在身边」，审阅新增）
- **核心改进点**：不采集任何新权限的用户行为，仅基于产品**内部已有数据**（上次对话时间、是否深夜发消息、对话频率、记忆库主题）让角色在合适时机表达「陪伴感」与「记得你」——例如深夜发消息后角色开场「你还没睡呀」、隔天重提昨晚话题。本质 = 记忆（F）+ 时机（B），是「陪在身边」的最简、无侵入落地。
- **实施范围**：并入 B（自发动机的触发时机）与 F（记忆引用的触发增强），不单独立任务；`PromptBuilder` 注入「陪伴感知」片段。
- **预期效益**：零新权限获得「它知道我最近的生活」的陪伴感；为 v2.0「从聊到帮」的「角色与用户同在」积累体验基础。
- **红线**：绝不以任何形式采集需要额外权限的用户行为。A' 与「行为观察」的根本区别：A' 只看 App 自己拥有的数据，观察则侵入用户设备外的生活。

### 方案 B · 事件驱动自发动机（解决 P-02）

- **核心改进点**：把「闹钟+概率」升级为「事件+动机」——用角色记忆中的「事」（用户提过光羽、一起喝过奶茶、上次约好明天见）作为触发器：满足触发条件（时间/关系/记忆主题）时，以"因某件事而起意"的方式发起互动（例：因记得你昨天说过喜欢奶茶 → 主动来聊）。保留定时窗口兜底，但优先走事件驱动。
- **实施范围**：`InteractionAutoExecutor` 升级（事件候选生成器）+ 记忆主题关联 + 互动开场白注入"因事"。
- **预期效益**：主动行为有因果感、可解释（"因为你提到过…所以我来了"），从"被调度"变"自发想起"。
- **变体**：B1 仅"记忆主题→互动话题"（成本低，已部分具备）· B2 完整事件触发器（含冷却/去重升级）。

### 方案 C · 关系事件系统（解决 P-03）

- **核心改进点**：为「角色-角色」/「角色-用户」关系引入「共同经历事件」——每次互动记录事件（场景/主题/氛围/关键内容），好感度变化附注事件；关系页显示"我们之间发生过的事"（里程碑式叙事：第一次见面→第一次深夜谈心→关系升温）。事件参与 prompt，让对话有"我们经历过"的连续性。
- **实施范围**：`ConversationRelationship` 扩展事件表（或复用 interaction\_turn）+ 互动中心「关系故事」区 + PromptBuilder 事件注入。
- **预期效益**：关系从"数值"变"叙事"，陪伴深度显著提升；与记忆系统天然衔接。
- **变体**：C1 仅记录+展示事件时间线 · C2 事件参与对话上下文（完整）。

### 方案 D · 新手上手与功能可发现性（解决 P-04）

- **核心改进点**：① 首次启动引导（2\~3 步：你是谁→她们是谁→能做什么）；② 入口重构——互动中心/记忆可视化/自动驱动从二级入口提为「主界面可发现」（会话列表角色卡显示状态、顶栏或首页宫格入口）；③ 空态引导文案（"长按试试"）。
- **实施范围**：`MainActivity`/ConversationList 首启向导 + 入口布局调整 + 各页空态。
- **预期效益**：新用户 3 分钟内建立"这是活在手机上的真人"的心智；功能发现率提升。
- **变体**：D1 仅首启引导 · D2 引导+入口重构（推荐）。

### 方案 E · 人设约束层（解决 P-05，远期候选）

- **核心改进点**：本地小模型（Qwen2.5-1.5B 量化 GGUF + llama.cpp/NNAPI）做人设守门与输出审核（企划书 4.4.3 输出审核），云端回复过审后放行；或退一步做「prompt 强化 + 输出规则校验（正则/关键词拦截跳出人设）」。
- **实施范围**：本地推理接入（大）或 PromptBuilder 强化（小）。
- **预期效益**：人设稳定性硬保证；离线兜底。
- **⚠️ 前置**：先做 1.5B 在 K60 的内存/时延实测（ROADMAP 已注明），不达标不立项。

### 方案 F · 记忆主动引用增强（解决 P-06）

- **核心改进点**：① 检索升级——top-K 提升 + 相关性重排（结合 FTS/时间衰减/情感权重）；② 触发增强——在"合适时机"（用户提到相关主题/开场/深夜）主动引用记忆；③ 提取质量——增加更正确认闭环与脏数据清理工具。
- **实施范围**：`MemorySearchService` + `MemoryRepository` + `PromptBuilder`。
- **预期效益**：记忆"被感知"率提升（命中率目标 ≥80%），强化"它记得我"的核心卖点。

### 方案 G · 性能与工程质量（解决 P-07/08/09）

- **核心改进点**：① 列表分页/懒加载（会话、消息、记忆）；② 流式 UI 节流（delta 合并按帧渲染）；③ 自动化回归集（核心链路：聊天/记忆/互动的 UI 冒烟 + Room 迁移升级测试）；④ 发布收尾（Release v1.0.0 + CHANGELOG 完整）。
- **实施范围**：数据层 + UI 层 + 测试工程 + 发布。
- **预期效益**：千条数据 60fps；任意版本升级 0 崩溃；每次改动回归有据可查。

## 3. 多维度复杂度评估

### 3a. 实施复杂度评估（评分体系）

**量化评分标准**（每维度 1\~5 分，5=最高成本/最高风险）：

| 维度   | 权重   | 1 分（低）         | 3 分（中）              | 5 分（高）             |
| ---- | ---- | -------------- | ------------------- | ------------------ |
| 技术难度 | 0.30 | 纯 UI/配置改动，无新依赖 | 涉及状态机/新表/新调度，复用现有模式 | 涉及本地推理/复杂算法/跨层改造   |
| 资源需求 | 0.25 | 仅现有真机+现有依赖     | 需新增少量数据模型/配置        | 需新硬件/大模型/新依赖库      |
| 时间成本 | 0.25 | ≤1 个任务点闭环      | 2\~4 个任务点           | ≥5 个任务点或跨多阶段       |
| 潜在风险 | 0.20 | 可完全回滚，无副作用     | 有数据迁移/行为变更风险，可控     | 涉及系统权限/模型效果/兼容性不确定 |

### 4.2 优选组合与实施优先级

## 一、必须优先讨论的点：方案 A 里那段“观察用户行为”

你特别标注的那段：

> 会话角色存在于用户的移动设备上，所以某种程度上来说就是一直陪在用户身边，结合后续会话用户可以控制设备，（应该做不到实时观察，那就定时观察用户行为？有点怪怪的）你看一下吧，我一个人想不出来什么好的。

我的建议很明确：**不要做“观察用户行为”**，包括定时观察。理由有三：

1. **隐私与伦理风险**：定时采集用户行为（打开哪些 App、停留时长、解锁频率、位置等）会触碰系统权限和用户信任边界，即使本地处理也容易引发不适，和产品“陪伴感”的基调相悖。
2. **实现复杂度高、收益不稳定**：要可靠地推断用户状态（在忙、在休息、心情如何）需要大量信号和模型，单人项目难以做好，做出来也容易变成“监视感”。
3. **方向跑偏**：方案 A 的核心价值是“角色有自己的生活节奏”，而不是“角色知道用户在干嘛”。后者是另一条产品线，应该单独评估，不要混进 A。

更合适的替代方向有两个，按推荐程度排序：

- **只做角色侧生活状态**：状态机完全基于角色卡设定 + 真实时间，不依赖用户行为。用户打开 App 时看到“TA 在午睡 / 在看书 / 在写代码”，这已经能强烈传递“活着”的感觉。这也是方案 A 原本的主体，建议保持不变。
- 如果确实想增加“陪伴感”，可以做**基于交互行为的软感知**：例如用户多久没打开 App、上次对话时间、是否在深夜发消息，这些数据本来就属于产品内部，不需要额外权限，可以用来调整角色开场白（“你昨天很晚才睡吧”），但这属于 B/F 的范畴，不要放进 A。

所以 A 方案不需要改，把那段疑虑划掉即可。

***

## 二、实施顺序建议微调：D 不要最先做，或只做轻量版

原顺序是 D → A → C。我理解 D 性价比最高、能快速提升新手体验，但有个问题：

**D 的引导内容会指向 A/C 的功能**，比如“角色卡片显示此刻状态”“互动中心有共同经历”。如果 A/C 没落地，引导就会变成“功能还没做完就教用户用”，体验反而更差。

建议调整为两种方案二选一：

- **方案 1（推荐）**：A（状态机基础版）→ C（关系事件基础版）→ D（完整引导）→ B → F/G。\
  先把“角色有生活”“关系有故事”做出来，再做引导，引导才能言之有物。
- **方案 2**：D 只做最轻量的首启 2\~3 步引导 + 空态文案，不涉及入口重构；等 A/C 完成后再补入口提级和完整引导。

如果你更在意快速改善新用户流失，方案 2 也可以接受，但需要明确 D 拆成两个任务点，避免引导承诺未完成功能。

***

## 三、Phase 0 基线数据缺失，需要补具体采集方法

方案里写了要采集“真人感自评 / 功能发现率 / 记忆命中率抽样”，但没给方法和工具。建议在 Phase 0 明确：

- 真人感：沿用前序八维评价表，找 3\~5 个真实用户或自己以新用户视角打分，记录基线。
- 功能发现率：用真机录屏 + 首次使用观察，统计 3 分钟内找到互动中心/记忆/自动驱动的比例。
- 记忆命中率：准备 5 段含明确事实的对话脚本，隔天再问相关问题，统计模型是否正确引用记忆。

否则 M1/M2/M3 的“≥85%”“≥80%”没有可比基线，验证会失真。

***

## 四、几个工程/实现层面需要提前确认的点

1. **关系事件与记忆系统的边界**\
   C 方案说“扩展 ConversationRelationship 或复用 interaction\_turn”。建议明确：关系事件是独立表，还是作为记忆的一种类型？如果独立，要注意与 MemoryRepository 的查询一致性；如果复用，要加事件类型字段并避免脏数据混入。这会影响 Room 迁移和后续查询，越早定越好。
2. **性能测试的数据准备**\
   “千条数据 60fps”目前可能还没有千条真实数据。建议在 G 里增加一个开发用的种子数据生成脚本（批量插入消息/记忆），用真机压测验证分页和懒加载，否则 M3 无法验收。
3. **自动化回归集的范围**\
   单人开发做完整回归集成本高，建议先只做**核心链路冒烟**：启动 → 建会话 → 发消息 → 流式回复 → 记忆写入 → 互动入口打开。范围小、可跑通即可，不要追求全量覆盖。

***

## 五、对新增需求 N1\~N4 的意见

我建议**全部批准**，但有两个调整：

- **N1 拆成两步**：先做“状态展示”（角色卡片显示此刻在干嘛），再做“状态参与对话与互动调度”。第一步极快，能立刻提高真人感感知。
- **N4 不单独排在最前**，按上面第二点的顺序，放在 A/C 基础版之后，或者拆成“轻量引导”先行。

N2、N3 没有异议，按方案执行即可。

***

## 六、总结

这份方案可以进入执行，但建议先做以下三项调整：

1. 方案 A 明确**不做用户行为观察**，保持角色侧生活状态。
2. 实施顺序改为 **A/C 基础版 → D 完整引导 → B → F/G**，或 D 拆轻量先行。
3. Phase 0 补上基线采集的具体方法和工具。
