## 1. 项目背景分析

**产品现状**：EdenCourt 是一款「类微信、角色扮演、跨会话记忆」的 Android AI 应用，v1.3.0 已完成「性能/稳定性/真人感」三支柱（冷启动 ≤3s、内存 ≤200MB、0 FATAL、真人式短句交互、跨会话记忆、角色差异化）。当前角色只能通过**文字**与用户交流。

**问题与机会**：
- 用户高频交互是"看消息"（静止场景），缺少"听角色说话"的沉浸入口。
- ROADMAP 已把「语音出」规划为 2.3 多模态的核心组成，是本阶段最自然的体验升维。
- 用户明确诉求（见方案文档 §2）：**① 音色可自定义 ② 音调高低起伏可调 ③ 中英日三语**。

**立项边界**：本计划把 2.3 的「语音输出（TTS）」提前落地为 **v1.4.0**；语音输入（ASR）、实时音色混合、语音克隆、群聊雏形**不在 v1.4 首发范围**（分别列 v1.1/v1.2/后续版本）。

**硬前置门槛（红线）**：MeloTTS 中文 ONNX 在 K60 真机实测（实时率 >2× / 内存增量 <200MB / 音质自然不机械）**通过才进入正式开发**；不通过则回溯方案（换转换路径 / 换引擎 / 与用户重议质量标准）。

## 2. 目标设定

### 2.1 总体目标

在 EdenCourt 内落地**端侧（离线）中文语音输出**：角色消息可被自然读出，音色/音高/语速/情感可调，全程不联网、不上传音频，符合本地优先原则。

### 2.2 量化验收指标（gate）

| 维度 | 指标 |
|---|---|
| 实时率 | ONNX 推理实时率 > 2×（1 秒音频合成耗时 < 0.5s） |
| 内存 | 运行期内存增量 < 200MB |
| 音质 | 分层：v1.0 自然不机械（用户试听确认）；v1.2 起 CosyVoice 2 往「接近星野」进阶 |
| 稳定性 | 覆盖安装 + 核心链路冒烟 0 FATAL |
| 范围 | v1.0 交付中文 TTS + 音色选择 + 音高/语速滑杆 + 情感预设 + 试听自定义文本 |

### 2.3 分阶段目标

| 阶段 | 目标 | 出口 gate |
|---|---|---|
| 前置验证（P0） | 证明 MeloTTS 端侧 TTS 可行（主引擎已定） | 音频样例用户通过才立项 |
| v1.0 首发 | 中文 TTS 完整闭环 | 编译 + 单测 + 真机 + 发布 |
| v1.1（后续） | 多语言（英/日）+ 语言路由 | — |
| v1.2（后续） | 自定义音色导入 + 零样本克隆 + 指令式情感/韵律（CosyVoice 2） | — |

## 3. 技术选型

### 3.1 推理运行时：sherpa-onnx（主）+ ONNX Runtime Mobile（辅）

- **sherpa-onnx**：事实标准端侧语音推理框架，提供 Android AAR（~56MB）、Kotlin/Java API、OfflineTts；已有多例 Android 真机落地（含华为无 GMS）。
- **ONNX Runtime Mobile**：CosyVoice 2（零样本音色克隆 + 指令式情感/韵律）等未纳入 sherpa 的模型走此路径，模型按需集成。

### 3.2 TTS 引擎：MeloTTS 中文（已定主引擎，2026-08-31 试听定案）

双候选本机试听（用户 2026-08-31 人工定案）：

| 对比 | MeloTTS 中文（✅ 选中） | Kokoro-82M（❌ 淘汰） |
|---|---|---|
| 中文音质 | ✅ 整体自然可用 | ❌ 停顿卡顿明显、机械 |
| 英语 | ✅（中英混合） | ✅ |
| 日语 | ⚠️ 现成 ONNX 缺口，需自导出 | ⚠️ sherpa 现成 ONNX 待确认 |
| 音色数 | 单音色 | 103 个 |
| 体积 | 162.5MB@44.1kHz | 310.5MB@24kHz |
| 桌面 RTF | 0.25（4线程） | 0.41~0.43 |

**结论**：主引擎 MeloTTS 中文（中文音质强项，单音色，v1.0 保底）；Kokoro 中文已淘汰，仅作 v1.1 处理英/日的候选（语言路由 + 混合引擎，见咨询稿 Q2）。

### 3.3 语音参数实现

- **音色**：v1.0 预设音色 + 音高/语速/情感变化做差异；自定义音色导入 + 零样本克隆 + 指令式情感/韵律（**CosyVoice 2**）列 v1.2。
- **音调**：后处理 **pitch shift**（±2 半音）+ 语速（0.8~1.2×）+ 情感预设模板（平静/开心/严肃/温柔/急切）。
- **文本韵律预处理**：标点/省略号/强调轻处理，不插入奇怪符号。

### 3.4 播放

- AudioTrack / ExoPlayer 播放合成 PCM；下载/播放可见反馈（横幅 + 进度）。

### 3.5 架构：Provider 模式

- `TtsEngine` 接口 + 语言路由 + 云端引擎预留扩展点（用户配 API Key 才可见）。

## 5. 时间节点规划（里程碑）

## 6. 风险应对策略

| # | 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|---|
| R1 | MeloTTS 日语 ONNX 缺口 | 高 | 三语诉求受阻 | 主引擎 MeloTTS 中文已定；日语自导出或混合引擎（英/日→Kokoro）留 v1.1 定 |
| R2 | 端侧实时率 / 内存不达标 | 中 | 立项中止 | INT8 量化、换更小模型（Kokoro 82M）、降采样率 |
| R3 | 音色克隆模型偏大端侧跑不动 | 中 | v1.2 功能延后 | 量化/剪枝（有 RVC-Android 先例）；v1.0 先预设音色 |
| R4 | 个别字发音生硬（如「错」「窗」） | 中 | 用户不认可 | 调 noise/length 参数、韵律预处理、lexicon 特例/音素改造（待专家意见），必要时重议质量标准 |
| R5 | 模型体积致 APK 膨胀 | 低 | 安装包过大 | 运行时按需下载模型，不打进 APK |
| R6 | 英文单词超出 lexicon | 中 | 生僻英文读不出 | 自定义 lexicon 扩展 + 未知词回退规则 |

## 7. 任务拆分（模块化）

> 每个任务点：`工作内容 → 交付物标准 → 负责人 → 时限 → 依赖`。
> 负责人：**AI 执行（Flash 主）+ 用户审核**。一次只做一个任务点，人工审核后再推下一个。

## 9. 分工与协作方式

- **Flash（主执行）**：常规实现、模型集成、编译、单测、真机验证、文档维护。
- **pro（关键复核）**：引擎选型决策、数据模型/架构设计、发布前全面审核。
- **用户（人工审核）**：每阶段结束复核交付物（尤其 M4 立项 gate 的音频试听）、批准推下一个任务点。

> 协作节奏：AI 完成一个任务点 → 输出「交付物 + 操作流程 + 测试合格标准」→ 用户审核 → 推下一个。
