## 一、项目背景与立项理由

EdenCourt 是 Android 端 AI 角色扮演聊天应用，当前角色只能通过**文字**与用户交流。ROADMAP 把「语音出」列为 2.3 多模态核心组成。本计划将其提前落地为 **v1.4.0**，为用户增加「听角色说话」的沉浸入口。

**用户核心诉求（三条，需全部满足）**：
1. **音色可自定义**（不同角色/会话有不同声音）
2. **音调高低起伏可调**（音高 / 语速 / 情感可调）
3. **中英日三语**（中文为主，英/日后续）

**硬性约束**：本地优先（推理离线、音频不上传）。

**音质目标（分层）**：v1.0 端侧「自然不机械」保底闭环；v1.2 起用 CosyVoice 2 往「接近星野」进阶（中长期目标）。

## 二、总体目标与分阶段路线

| 版本 | 范围 | 出口标准 |
|---|---|---|
| **v1.0（本阶段）** | 中文 TTS 完整闭环：合成 + 播放 + 音色选择 + 音高/语速滑杆 + 情感预设 + 试听自定义文本 | 真机实测实时率>2×、内存增量<200MB、音质用户认可、0 FATAL |
| **v1.1** | 多语言（英/日）+ 按语言自动路由 | 三语可合成 |
| **v1.2** | 自定义音色导入 + 零样本音色克隆 + 指令式情感/韵律控制（**CosyVoice 2**） | 音色/提示音频导入生效 |

**明确不做（范围冻结）**：语音输入 ASR（后续另立项补闭环）、实时音色混合滑块、语音克隆进 v1.0。

## 三、技术选型与理由

### 3.1 推理运行时：sherpa-onnx

- Android AAR ~56MB，Kotlin API（OfflineTts），端侧 TTS 事实标准，多例 Android 真机落地。
- 备选 ONNX Runtime Mobile（CosyVoice 2 等未纳入 sherpa 的模型用）。

### 3.2 TTS 引擎：MeloTTS 中文（已定主引擎）

双候选真机/本机对比（用户 2026-08-31 人工试听）：

| 对比 | MeloTTS 中文 | Kokoro-82M（中英） |
|---|---|---|
| 音质（试听） | ✅ 整体自然可用 | ❌ 停顿卡顿明显、机械（被淘汰） |
| 音色数 | 单音色 | 103（中文女55/男45） |
| 三语 | 中英混合；日语 ONNX 需自导出 | 中英原生；日语待确认 |
| 模型体积 | 162.5MB@44.1kHz | 310.5MB@24kHz |
| 桌面 RTF | 0.25（4线程） | 0.41~0.43 |

**结论**：主引擎 MeloTTS 中文（中文音质是它强项）；Kokoro 中文不合格，仅作为 v1.1 处理英/日的候选（语言路由 + 混合引擎策略待定，见问题 Q2）。

### 3.3 语音参数实现

- **音色**：v1.0 预设音色（Mel 单音色 + 音高/语速/情感变化做差异）；多音色/自定义音色走 v1.2 **CosyVoice 2**（零样本克隆 + 指令式情感/韵律）。
- **音调**：后处理 **pitch shift（±2 半音）** + **语速 0.8~1.2×** + **情感预设模板**（平静/开心/严肃/温柔/急切）。
- **韵律预处理**：标点/省略号/强调轻处理。

### 3.4 架构：Provider 模式

- `TtsEngine` 接口 + 语言路由 + 云端引擎预留扩展点（用户配 API Key 才可见），保证可扩展可替换。

## 四、质量与验收标准（硬门槛）

1. 真机（K60，骁龙 8+ Gen1）中文合成**实时率 > 2×**（1s 音频 < 0.5s 合成）
2. 运行期**内存增量 < 200MB**（162.5MB 模型 + 运行时）
3. 音质「自然不机械」，**用户人工试听确认**
4. 覆盖安装 + 核心链路冒烟 0 FATAL
5. 首次使用引导下载模型（WiFi 提示），推理全程离线

## 五、资源与约束

- 模型 162.5MB（MeloTTS 中文），运行时下载、**不打进 APK**（防包体膨胀）；应用数据目录预留 300~500MB。
- 真机 1 台（K60，已有）；云 API 预算不变（纯端侧）。

## 七、请专家评审的开放问题（核心求助，按优先级）

### Q1 音色可自定义的最优路线（v1.0 保底 / v1.2 进阶）

MeloTTS 官方 sherpa 中文仅单音色。用户要「音色可自定义」，已定**分层路线**：v1.0 端侧 MeloTTS 单音色保底；v1.2 用 **CosyVoice 2** 实现自定义音色 + 指令式情感/韵律控制。请专家评估：

1. **v1.0 保底方案是否足够**：MeloTTS 单音色 + 音高/语速/情感变化做差异化，能否满足用户「音色可自定义」的初级需求？还是 v1.0 也需引入社区多说话人 MeloTTS（待核实：是否有 sherpa 直接支持的多 speaker 中文版本）？
2. **CosyVoice 2 端侧落地（v1.2）**：零样本音色克隆 + 指令式情感/韵律控制，在 Android（ONNX Runtime）的可落地性、模型体积、实时率？最小可用规格如何？
3. **音色输入格式**：CosyVoice 2 的音色用「音频 prompt + 音色嵌入」还是别的格式导入？与 sherpa-onnx 的离线架构如何衔接（v1.2 是否引入第二运行时）？

### Q2 中英日三语的落地策略

- 中文：MeloTTS（已定）
- 英语：MeloTTS 中英模型与 Kokoro 均可（待实测对比）
- 日语：MeloTTS 现成 ONNX 有缺口（需自导出）；Kokoro 日语是否有 sherpa 现成 ONNX 需另确认
- 推荐：**语言自动路由 + 混合引擎**（中文→MeloTTS，英/日→Kokoro）是否合理？还是 v1.1 直接自导出 MeloTTS 日语保持单一引擎？从端侧体积（两个引擎 ≈ 470MB）和音质角度怎么权衡？

### Q3 MeloTTS 中文个别字发音不准的修复

- 现象：用户试听长句「你好呀，今天天气不错。窗外的樱花开了，我给你泡了杯热奶茶，慢慢喝。」，参数 2~5 整体自然，但「错」(c+uo 4声)、「窗」(ch+uang 1声) 两字发音影响明显。
- 已排查：lexicon 映射正确（窗=ch uang 1、错=c uo 4）；音素 token 齐全（c/ch/uang/uo 均在 tokens.txt）。备注：tokens.txt 无独立声调数字 token，但这仅是 symbol 表的组织方式，MeloTTS 前端经 pypinyin 已将声调编码进音素序列，未必是声调信息丢失；两字发音生硬更可能是模型对该音节的声学输出局限，根因待专家判断，不预设方向。
- 请给：针对单个/部分字发音问题的**可落地方案排序**（参数微调 / 音素序列改造 / 该字 lexicon 特例 / 社区模型替换 / 训练层），并说明 sherpa-onnx Android 端各自可行性。

### Q4 真机性能优化（162.5MB 模型）

- 官方 `model.int8.onnx` 是损坏占位（133B），INT8 需自行量化 → 真机量化/降采样/换小模型的推荐路径？
- sherpa-onnx Android 端加载 162.5MB FP32 模型到 RAM 的实际开销、`num_threads`/provider 建议？
- 实时率>2×、内存<200MB 这两条硬门槛在骁龙 8+ 上是否现实？不达标时的次优方案？

### Q5 长句断句与韵律

- MeloTTS 长句（>30 字）合成质量与 `max_num_sentences`/断句策略建议？
- 中文情感表达（开心/温柔/急切）在端侧 MeloTTS 上的可实现度（有无 emotion 维度或只能靠 pitch/speed/韵律）？

## 八、关键数据附录

- 测试长句：`你好呀，今天天气不错。窗外的樱花开了，我给你泡了杯热奶茶，慢慢喝。`
