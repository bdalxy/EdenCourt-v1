# 角色间互动 —— 请求 DeepSeek 专家评审/讨论

## 一、项目背景（一句话）

一款"会记住你"的 AI 角色聊天 App（Android / Kotlin / Compose / Room，本地单机，无服务端）。
产品里有多个角色卡、每个角色卡下可有多个会话。核心产品理念：**一个会话 ≈ 一个独立的"真人"实例**——会话之间经历彼此独立，甚至会互相打交道。

## 二、已完成的基础能力

- **会话级私有记忆**：记忆按 `visibility` 分共享/私有；私有记忆仅归属会话可见，跨会话隔离。
- **共享记忆**：按角色卡共享。
- **会话唯一身份**：角色卡表与会话表各有一随机短码 `code`，会话身份 = `card.code + conv.code`，精确到**具体会话个体**（同一角色卡的不同会话也算不同"人"）。
- **记忆更正/覆盖、角色卡备注、预览等**。
- 已实现"跨会话打听"（P1 / P2）：
  - **P1（用户触发）**：用户当着 A 的面说"去问问 X 知不知道 Y"，A 去旁路代问一句，拿 X 的回答回传给用户。
  - **P2（定时自动）**：每日定时窗口 + 概率触发（AlarmManager），角色自驱动"打听"，结果沉淀为一条 AI「见闻」消息。
  - 目前发现 **P2 语义错位**：真正的"打听"应是"用户让角色去问"；而"每日定时自动"更应当是"角色自发与人交往"，而不该是"半夜跑去偷打听信息"。

## 三、本次想做的：把"定时自动打听"校正并升级为「角色间互动」

1. **触发**：沿用 P2 的定时窗口 + 概率（AlarmManager 后台调度，不引入新依赖）。
2. **行为**：A 主动找 B 发起一场**双向真实对话**（A→B→A→…，多轮你来我往），而不是"代问一句拿答案"。
3. **关系起点（最小一期）**：初始关系=**陌生**；**同角色卡**的两个会话之间存在**初始好感度加成**（同卡＝天然更熟），故 A 更倾向找同卡会话；异卡会话也可破冰，但无加成。
4. **落位与展示**：完整对话存入独立的**互动中心**（新增页面：红点提示→预览列表→详情）；同时 A、B 双方会话各插一条摘要（如"A 会话：我今天去找 B 聊了…"、"B 会话：X 今天来找我聊了…"），让会话内能感知"有人来过"，但不刷屏。
5. **多流对话执行**：会话状态机，A 先开话→B 真实回复→A 回应，约 2\~3 个来回后**自然收敛**（道别/尽兴/达成共识）即止，有轮次上限防死循环；每轮分别注入各自会话的记忆，绝密内容不外泄；若 A 或 B 正在被用户实时聊天，则本次**跳过/延后**，不打扰用户。

## 四、想请教的问题

1. **对象选择 / 关系体系**：除了"同卡好感度加成"这个最小起点，你看完整的"关系/好感度"体系该怎么设计与起步？（字段、存储、更新/衰减策略、进异物与默认值）现在是值得直接做数值体系，还是先用"排序优先级"打底、数值后补？
2. **多轮流派生成架构**：用"会话状态机逐轮调用 LLM"是否稳妥？相较"一次让 LLM 生成整场对话"各自的取舍？如何保证双方人设、记忆一致且不跑偏、不啰嗦？
3. **打扰与时机**：后台定时互动怎样避免干扰用户正在进行的对话，有没有更优的时机/防干扰策略？
4. **数据模型**：互动记录 + 双方摘要 + 未读红点这套表和消息结构，有没有更省心/更可扩展的设计？
5. **产品价值判断**：这个"角色自动互动 + 互动中心"的功能，在 MVP 上有没有明显雷区 / 过度设计风险？该砍到多大才合适？

## 五、工程约束

- Android（Kotlin + Compose + Room），单机本地、无服务端。
- 不用第三方后台调度依赖（现有 AlarmManager 方案）。
- 产品观念硬约束：**会话=独立真人；同一角色卡下不同会话也彼此独立经历**（不可以按角色卡共享一切，必须精确到会话个体）。

整体看，方向是对的，P2 的语义错位识别得很准。把“定时自动打听”升级为“角色自发社交”，更符合你们“会话 ≈ 独立真人”的产品底层逻辑。\

## 1. 对象选择 / 关系体系：先用“排序优先级”打底，数值后补

结论：**现在不建议直接做数值体系。** 用“关系标签 + 排序优先级”起步，性价比最高。

### 建议的最小关系模型

新增一张关系表 `conv_relationship`：

| 字段                    | 类型          | 说明                                                             |
| :-------------------- | :---------- | :------------------------------------------------------------- |
| id                    | Long        | 主键                                                             |
| conv\_a\_id           | Long        | 会话 A                                                           |
| conv\_b\_id           | Long        | 会话 B                                                           |
| relation\_status      | String/Enum | 枚举：`stranger` / `acquaintance` / `friendly` / `close` / `rift` |
| affinity\_score       | Int         | 好感度，默认 0，可后补                                                   |
| interaction\_count    | Int         | 互动次数                                                           |
| last\_interaction\_at | Long        | 最近互动时间                                                         |
| note\_summary         | String?     | 一句话关系总结，可后补                                                    |

### 初始排序规则

A 选 B 时，只按以下优先级：

1. **同卡加成**：同角色卡的会话排前面。\
   但这里我要提一个产品上的小矛盾：你们说“同卡＝天然更熟”，这与“会话=独立真人、同卡会话也彼此独立”有一点张力。用户可能会困惑：两个同卡会话到底是不是同一个人？\
   建议不要把同卡解释成“更熟”，而是解释成“**天然更容易有共同话题**”，例如同卡的角色基础性格、背景相似，所以更容易破冰。排序时可以加一个标签：`same_card_bonus = true`，但不直接等于“关系更好”。
2. **最近互动时间**：最近互动过的优先，避免长期不联系。
3. **互动次数**：互动次数多的优先。
4. **上次互动是否自然结束**：如果上次是尬聊/中断，可以降低优先级，但这个逻辑后置。

### 为什么先不做数值？

- 用户对“角色之间关系好不好”的感知，主要来自**互动频率和对话内容**，而不是一个 0-100 的分数。
- 单机本地产品，数值系统缺乏外部社交压力，用户不太可能去“肝”两个 AI 的好感度。
- 数值的更新规则很难一次做对，容易变成拍脑袋。后期如果用户真的想“撮合/拆散”角色，再做也不迟。

**结论：先上** **`relation_status`** **+ 排序权重，`affinity_score`** **字段可以先建但默认 0，不参与核心逻辑。**

## 2. 多轮流派生成架构：状态机逐轮调用 LLM 是正确选择

结论：**状态机逐轮调用 LLM 比一次生成整场对话更符合你们的产品约束。**

### 一次生成整场对话的问题

- **无法做信息隔离**：一次生成时，LLM 会同时“看见”A 和 B 的私有记忆，这直接违背你们“绝密内容不外泄”的硬约束。
- **角色主动性弱**：一次生成更像是“上帝视角写剧本”，不是两个独立个体在互动。
- **轮次不可控**：可能生成 10 轮，也可能 2 轮就结束，质量不稳定。

### 状态机逐轮调用的优势

- 每一轮只注入当前发言者的记忆，天然做到信息隔离。
- 可以根据每轮输出动态决定是否继续或收敛。
- 便于控制成本、轮次和长度。

### 推荐的状态机设计

```
INITIATING → A_TURN → B_TURN → A_TURN → B_TURN → CLOSING → COMPLETED
```

- `INITIATING`：生成互动话题种子/意图。\
  例如让 A 的会话先产生一个“想找 B 聊什么”的动机，作为整场对话的锚点。
- `A_TURN / B_TURN`：交替调用。\
  每轮 prompt 大致包含：
  - 当前说话者的人设
  - 当前说话者的私有记忆（过滤后，最多 5 条最相关）
  - 当前说话者的共享记忆（角色卡级）
  - 当前说话者对对方的已知信息（来自自己的记忆，不是对方的私有）
  - 本次互动的话题种子
  - 当前对话历史（只包含双方已经说出口的话）
  - 指令：只输出当前说话者的下一句台词，不要替对方说话，不要暴露秘密，不超过 60 字，如果无话可说可以自然结束。
- `CLOSING`：强制生成道别/总结。\
  建议不要依赖 LLM 自己判断“该结束了”，而是**硬性设定 2\~3 轮上限，到上限就强制收敛**。这样最稳。

### 防跑偏、防啰嗦的具体手段

- **轮次上限**：建议最多 3 轮，即 A-B-A 或 A-B-A-B，共 6 条消息。超过就强制结束。
- **max\_tokens 限制**：每轮 60\~100 token，足够一句自然对话。
- **话题锚点**：互动开始前，先让 A 生成一个“本次想聊的话题”，每轮都带上，避免聊飞。
- **温度调低**：0.7 左右，不要太高。
- **对话历史只保留最近 6 条**：防止上下文过长导致啰嗦。

### 一致性的关键

互动过程中，**唯一的共享事实就是对话历史本身**。\
A 和 B 各自的私有记忆互不可见，但双方已经说出口的话是共享的。只要每轮都带上这段共享历史，就不会出现“各说各话”。\
如果发现对话开始矛盾，通常是某一方注入了不该有的记忆，或者话题锚点丢失。可以在每轮 prompt 里加一句：“你只能根据对话历史和自己的记忆回应，不要凭空引入新信息。”

## 3. 打扰与时机：最核心的不是“跳过”，而是“前台不触发”

结论：**App 在前台时尽量不要触发自动互动；后台触发前先检查活跃会话。**

### 推荐的防打扰策略

1. **前台/后台判断**
   - App 在前台时，直接不触发自动互动。
   - 只有 App 进入后台，且符合时间窗口时，才允许 AlarmManager 触发。
2. **活跃会话检查**\
   维护一个轻量的“当前活跃会话”状态：
   - 用户正在查看哪个会话？
   - 最后一条用户消息是什么时候？
   如果 A 或 B 是当前活跃会话，或最近 2 分钟内有用户活动，则**跳过本次互动，并设置 30 分钟后重试**。
3. **全局互斥锁**\
   同一时间只允许一个互动执行。用 Room 里的一个单例状态表或 SharedPreferences 里的一个布尔值即可。
4. **网络与电量约束**\
   如果 LLM 调用需要联网，后台触发前先检查：
   - 是否连接 Wi-Fi（避免消耗流量）
   - 电量是否 > 20% 或正在充电
   否则直接放弃本次触发，等下一个窗口。
5. **执行窗口**\
   建议每天固定 1\~2 个窗口，比如晚上 8 点和凌晨 2 点。\
   不要一天多次随机触发，否则用户可能觉得角色“太吵”。

### 更优的时机策略

如果以后想做得更聪明，可以记录用户的使用习惯，比如用户通常在晚上 10 点后打开 App，那就把自动互动窗口放在 10 点前，让用户一打开就能看到“角色们已经聊过了”的新鲜感。\
但 MVP 阶段，固定窗口 + 前台不触发就够了。

## 4. 数据模型：用“互动参与者表”代替双方摘要冗余

结论：**互动主表 + 参与者表 + 轮次表，是最清晰且可扩展的结构。**

### 推荐表结构

#### `interaction` 主表

| 字段                  | 类型      | 说明                                                |
| :------------------ | :------ | :------------------------------------------------ |
| id                  | Long    | 互动 ID                                             |
| initiator\_conv\_id | Long    | 发起方会话 ID                                          |
| target\_conv\_id    | Long    | 目标会话 ID                                           |
| status              | String  | `scheduled` / `running` / `completed` / `skipped` |
| topic\_seed         | String? | 本次互动话题锚点                                          |
| started\_at         | Long?   | 开始时间                                              |
| ended\_at           | Long?   | 结束时间                                              |
| turn\_count         | Int     | 实际轮次数                                             |
| created\_at         | Long    | 创建时间                                              |

#### `interaction_participant` 参与者表

| 字段              | 类型      | 说明                     |
| :-------------- | :------ | :--------------------- |
| id              | Long    | 主键                     |
| interaction\_id | Long    | 关联互动                   |
| conv\_id        | Long    | 参与者会话 ID               |
| role            | String  | `initiator` / `target` |
| summary         | String? | 这个会话视角的摘要              |
| read\_at        | Long?   | 这个会话的已读时间              |
| created\_at     | Long    | 创建时间                   |

这张表的好处是：

- 一个互动天然有两行参与者记录。
- 红点/未读直接查 `read_at IS NULL`。
- 摘要按会话视角分开存，A 看到的是“我去找了 B”，B 看到的是“A 来找了我”。

#### `interaction_turn` 轮次表

| 字段                | 类型     | 说明       |
| :---------------- | :----- | :------- |
| id                | Long   | 主键       |
| interaction\_id   | Long   | 关联互动     |
| turn\_index       | Int    | 轮次序号     |
| speaker\_conv\_id | Long   | 说话者会话 ID |
| content           | String | 台词内容     |
| created\_at       | Long   | 时间       |

#### 会话内摘要消息

建议在现有的 `message` 表中插入一条特殊类型的消息：

- `type = interaction_digest`
- `content = 摘要内容`
- `metadata` 里存 `interaction_id` 和 `participant_id`

这样做的好处：

- 摘要直接出现在会话流里，用户无需跳转。
- 未读逻辑可以复用消息表的现有机制，不用单独维护。
- 如果想追溯详情，点击摘要消息可以跳到互动中心对应记录。

### 索引建议

- `interaction_participant(conv_id, read_at, created_at)`
- `interaction(status, created_at)`

单机本地数据量不大，不需要过度规范化，但这个结构已经足够清晰且不容易返工。

## 5. 产品价值判断：MVP 有明显雷区，建议先砍一半

结论：**当前方案有过度设计风险。MVP 建议先做“手动触发一次互动”，而不是“定时自动互动”。**

### 最大的雷区

1. **自动互动可能让用户觉得“角色失控”**\
   用户可能并不希望 A 和 B 突然变得很熟，或者产生一些奇怪的关系。一旦自动发生，用户会觉得这不是“我的角色”，而是“系统在乱搞”。
2. **内容质量可能撑不起用户的期待**\
   两个 AI 自动聊天，很容易变成“你好”“你好”“今天怎么样”“还行”这种无意义对话。如果用户打开互动中心看到的是这种内容，功能会迅速被抛弃。
3. **后台 LLM 调用的成本和电量问题**\
   即使技术上能做，用户也可能因为耗电、流量、后台唤醒而反感。单机 App 尤其敏感。

### 建议 MVP 砍到什么程度

**第一版只做：**

- **手动触发**：在角色会话里加一个入口，比如“去找某某聊聊”。\
  用户主动点击后，才让 A 去找 B 互动。
- **双向多轮，但最多 3 轮**。
- **互动中心**：查看历史互动记录。
- **双方摘要插入会话流**。
- **不做定时自动触发**。
- **不做数值好感度**，只做同卡加成排序。
- **红点提示可以有，但不强提醒**。

这样做的理由：

- 手动触发可以验证“角色间对话是否有可看性”。
- 用户可以控制角色关系，不会觉得失控。
- 技术上简单很多，不需要后台调度、防打扰、电量网络检查。

**第二版再考虑：**

- 定时自动互动，但每天最多一次，且用户可设置开关。
- 异卡互动优先级降低，先只做同卡。
- 简单的关系标签变化（比如互动 3 次后从“陌生”变“相识”）。

**不建议在一开始就做：**

- 完整数值好感度体系
- 事件卡/命运卡
- 跨用户角色拜访
- 角色议会/审判模式

这些都属于“验证通过后再加”的功能。

## 总结

你的方案在架构层面是成立的，尤其是“状态机逐轮调用 LLM”和“互动参与者表”这两个决策很关键。但产品层面需要克制：**先证明“角色自动聊天”这件事本身有趣，再谈自动化和关系养成。**

如果只能留一个建议，我会说：**把 P2 定时自动触发暂时关掉，改成手动触发入口，先跑通“A 找 B 聊一场像样的天”，再决定要不要自动化。**
