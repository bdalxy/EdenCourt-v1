# 记忆系统升级 · 页面设计方案

> 给谁看：产品 / 你（审核）。这版聚焦「记忆页面长什么样、有哪些区块、怎么交互」，技术实现只在支撑处提一句。
> 设计原则：**先让用户一眼看懂「AI 记住了什么」→ 能分类管理 → 能直观回溯演化 → 能随手个性化**。沿用樱羽浅色（陪>75%）。

## 七、性能与检索底座（统一入口）

- **统一记忆检索 `MemorySearchService`**：管理页搜索 + 上下文注入检索，统一走这一个入口，共用 FTS/索引；注入端限制 `top-K`（最相关 10~20 条），按 `importance/pinned/updatedAt` 排序。→ 同时解决「管理页搜索慢」与「生成上下文变慢」。
- **FTS 选用 `@Fts4` + `contentEntity` 自动同步**：删除/编辑记忆后索引同步消失，杜绝搜索结果残留旧数据。
- **中文检索**：写入前做轻量预处理（bigram + 长短词）提升命中；2 字短词/模糊词退 `LIKE`，但先按 `characterCardId/分类/时间` 缩小候选集（真机验证达标后固化）。
- **列表**：Paging 分页 + 组合索引；阶段一**不做 stickyHeader**（避免与 Paging 冲突），分组职责交给顶部分类 Tab，日期分组在阶段二时间轴体现。
- 统计/共现：后台线程或预计算明查，绝不阻塞 UI；输入 300ms 去抖 + 协程异步；主题沿用樱羽浅色（≥75%）。

## 八、阶段一字段清单（一步到位，避免二次迁移）

> 现状已含：`type(→category)、keywords、confidence、characterCardId、visibility(共享/私密)、isTopSecret、sourceConversationId、sourceMessageId、createdAt、updatedAt、isDeleted`。
> 阶段一在现表上一次性补齐（UI 可先不展示，但 DB 层到位，后续阶段二/三只做交互不再迁移）：

| 新增字段 | 说明 |
| --- | --- |
| `timeScope` | SHORT_TERM / LONG_TERM（生命周期） |
| `expiresAt` | 可空；短期记忆可设到期 |
| `isPinned` | 是否置顶 |
| `importance` | 普通 / 重要 |
| `locked` | 是否锁定（防误删） |
| `sourceType` | CHAT / USER_EDIT / SYSTEM |

配合：Room 迁移 v12；建 `category + timeScope + characterCardId + visibility` 组合索引。

## 九、落地顺序（吸收专家意见后）

1. **阶段一（地基）**：类型双维 + 字段一步到位(迁移 v12) + FTS4 contentEntity + Paging + 分类 Tab + 统一检索服务（同时覆盖注入）。**验收：5000+ 条搜索/滚动流畅；上下文注入也走新入口且 top-K 截断、查询不拖慢生成。**
2. **阶段二（可视化）**：详情页、时间轴、概览统计。
3. **阶段三（关联/个性化）**：**共现热词列表**（点击进对应记忆列表）→ 关系图谱降为远期候选；按类型专属操作；批量/导入导出。

## 十、决策点结论

- **Q1 分类**：`category×（个人信息/偏好/事件/技能/情景/关系/其他）+ timeScope（短期/长期）`，不缩水、不滥增（保留"其他"兜底）。
- **Q2 优先级**：先阶段一地基，不上可视化/图谱。
- **Q3 大数据**：FTS 现在就上（搜索与注入的共同底座）；Paging 上但阶段一简化（无 stickyHeader）；按 5000+ 验收。
- **Q4 关系**：先「共现热词列表」，图谱放远期。

## **一、整体判断**

这份方案可以作为升级底座来推，但有几处如果不在阶段一就定清楚，后面会返工：

1. **检索注入路径也要纳入阶段一**
2. **阶段一必须一次性补齐字段，避免二次迁移**
3. **FTS 中文方案要比现在写得更具体**
4. **Paging3 与 stickyHeader 分组存在冲突风险**
5. **关系图谱建议后置，先用共现热词列表替代**

下面逐条说。

***

## **二、关键问题与补强建议**

### **1. 检索注入路径也要在阶段一改造**

方案里痛点提到了：

> 检索注入 `LIKE %kw%` 无法走索引，条数增大后检索注入退化、生成变慢

但阶段一的 FTS 方案主要落在「记忆管理页搜索」上。\
如果生成上下文时的记忆检索仍然走 `LIKE '%kw%'`，那用户感知最明显的“生成变慢”问题还是没有解决。

建议阶段一增加一个统一的 **MemorySearchService / MemoryRetriever**：

- 管理页搜索走它；
- 注入上下文时也走它；
- 统一使用 FTS / 索引查询；
- 注入时限制 `top-K`，比如只取最相关的 10～20 条，并按 `importance / pinned / updatedAt` 排序。

这样阶段一才能真正解决“大数据不卡 + 生成不慢”。

***

### **2. 阶段一就要补齐字段，避免阶段二再迁移**

阶段二详情页需要这些能力：

- 置顶 / 取消置顶
- 设为重要
- 锁定 / 私密
- 可见性
- 来源会话 / 消息
- 是否生效
- 过期时间

但方案没有明确阶段一的 schema 字段清单。\
如果阶段一只加 `category/timeScope/expiresAt`，到阶段二做详情页时才发现还需要 `isPinned`、`importance`、`visibility`、`locked`、`sourceConversationId` 等，就会再发生一次 Room 迁移。

建议在阶段一设计表结构时直接加入：

**字段**

**说明**

`category`

类别

`timeScope`

SHORT\_TERM / LONG\_TERM

`expiresAt`

可空，短期记忆可设置

`isPinned`

是否置顶

`importance`

普通 / 重要

`visibility`

PRIVATE / SHARED / ROLE\_SCOPED

`locked`

是否锁定防误删

`sourceType`

来源类型，如 CHAT / USER\_EDIT / SYSTEM

`sourceId`

来源会话或消息 ID

`isActive`

是否参与注入

这些字段阶段一可能不全部在 UI 展示，但数据库层一次到位，后续阶段二、三只做交互，不再迁移。

***

### **3. FTS 中文方案要更明确，否则“搜索快了但搜不到”**

FTS5 默认 `unicode61` 对中文连续字符串的处理，不一定能支持你想要的子串匹配。\
比如用户搜「蓝釉」，但记忆里是「青蓝釉配方」，默认 tokenizer 可能无法命中。

建议三选一：

- **FTS5 trigram tokenizer**：支持子串匹配，但要求查询词至少 3 个字符，中文两字词会受限；
- **自定义分词 / n-gram 预处理**：在写入 `keywords` 或 `content` 前先做分词，比如用结巴或简单 bigram；
- **混合方案**：FTS 负责主搜索，短词 / 模糊搜索退回 `LIKE`，但先通过时间范围、角色卡、分类大幅缩小候选集。

这个点必须在阶段一真机验证，不能只是“可加结巴分词”一笔带过。

另外要注意：\
**FTS 虚拟表与主表同步**。Room 的 `@Fts4` 支持 `contentEntity` 自动同步，但 `@Fts5` 的外部内容同步需要额外确认。\
如果同步没做好，后续删除 / 编辑记忆后，搜索结果会残留旧数据。

***

### **4. Paging3 与 stickyHeader 分组有冲突风险**

Paging3 是扁平数据流，stickyHeader 需要稳定分组结构。\
如果数据按 `createdAt` 分页，而分组是前端根据当前页数据现算的，粘性头会在翻页时跳动或缺失。

建议二选一：

- **先不做 stickyHeader**，用顶部分类 Tab 承担分组职责；
- 若坚持 stickyHeader，则分组字段必须进入分页排序键，例如按 `category + createdAt` 查询并分页。

从阶段一可控性出发，我更建议前一种：\
阶段一用「顶部分类 Tab + 分页列表」即可，日期分组等放到阶段二时间轴里体现。

***

### **5. 关系图谱建议降级为“共现热词列表”**

方案阶段三要做关系图谱，节点是关键词，边是共现强度。\
这个想法没错，但实际产品上可能遇到：

- 关键词共现噪声很大；
- 图谱交互复杂度高；
- 5000 条记忆下，共现计算虽然能异步，但 UI 呈现和点击跳转逻辑成本不低。

建议阶段三先做：

- 高频关键词排行；
- 关键词共现热词列表；
- 点击热词进入对应记忆列表。

关系图谱放到远期候选，等热词列表验证有价值后再做。

***

## **三、决策点建议**

### **Q1：记忆分类口径**

推荐按你提的 `category` 扩展为：

> 个人信息 / 偏好 / 事件 / 技能 / 情景 / 关系 / 其他

同时叠加 `timeScope`：

> 短期 / 长期

不要只做「短期/长期 + 现有 4 类」，那样表达力不够，后续还得再改。\
但也不要让 `category` 无限膨胀，保留“其他”兜底即可。

### **Q2：阶段优先级**

明确推荐先做阶段一：

> 类型双维 + FTS + 索引 + Paging + 分类 Tab

可视化图谱、关系分析不要一开始就排进来，否则阶段一验收边界会模糊。

### **Q3：大数据方案是否按 5000+ 标准做**

建议：

- FTS：上，而且现在就上，因为它是检索注入和搜索的共同底座；
- Paging3：建议上，但阶段一可以简化，不做 stickyHeader；
- 测试数据按 5000+ 验收是合理的，因为记忆只增不减，早期不卡不代表以后不卡。

如果你实在觉得当前数据量小，不想引入 Paging3 复杂度，那至少也要：

- 限制注入查询条数；
- 管理页搜索走 FTS；
- 列表用简单分页或限制首屏加载数量。

但长期看，Paging3 成本不高，早做更稳。

### **Q4：关系图谱 vs 共现热词**

建议先做「共现热词列表」，图谱放远期。\
这样阶段三依然可验收，且避免过早进入高成本图可视化。

***

## **四、结论**

这份方案总体可以推进，尤其阶段一方向正确。\
但建议在正式拆 `PLAN.md` 前，先补三件事：

1. 补一张 **阶段一字段清单 / 表结构变更说明**；
2. 增加 **MemorySearchService 统一检索入口**，覆盖管理页搜索和注入检索；
3. 明确 FTS 中文方案与同步策略，避免阶段一验收时发现搜索不达标。
